# Отправка файлов в сеть (подпроект N1)

> **Статус проверки.** Код написан и покрыт юнит-тестами на искусственных событиях, но **на живой системе не проверен**. Не подтверждены: идентификаторы событий ETW, имена и форматы свойств, совпадение `FileObject` в событиях открытия и чтения, вид пути (NT-форма). Они собраны в `agent/internal/collectors/netupload/ids_windows.go` и помечены там как НЕ ПОДТВЕРЖДЁННЫЕ. Перед использованием человек должен от администратора запустить `go run ./cmd/etwprobe` (из `agent/`), сверить вывод с `ids_windows.go` и выполнить ручную проверку из раздела 6 (браузер и Telegram). Пока этого не сделано, считайте, что сборщик может не давать событий, даже если агент не пишет ошибок.

## 1. Что делает

Сборщик `netupload` (только Windows) находит отправку документа в облако или мессенджер по связке «процесс прочитал файл → тот же процесс отправил на адрес известного сервиса не меньше байт, чем размер файла». Для найденного файла агент снимает зашифрованную копию через существующий механизм артефактов и присылает событие `network/upload`. Дальше работает готовый конвейер: воркер инспекции проверяет содержимое правилами и создаёт инцидент. Блокировки нет: агент видит факт отправки уже после её начала. Текст сообщений и содержимое форм не читается (это подпроект N2).

## 2. Как работает

```
ETW: чтение файлов ─┐
ETW: отправка сети ─┼─▶ reads · dnsmap ─▶ matcher ─▶ artifacts (копия) + очередь событий
ETW: DNS ───────────┘                                    │
                                                         ▼
                                   сервер → воркер → правила → инцидент
```

Источник событий: библиотека `github.com/0xrawsec/golang-etw` (чистый Go, cgo не нужен). Агент открывает **одну сессию ETW на процесс** с именем `BarysGuard-NetUpload` и тремя провайдерами:

| Провайдер | События |
|---|---|
| Microsoft-Windows-Kernel-File | открытие (12), закрытие (14), чтение (15) файла |
| Microsoft-Windows-Kernel-Network | отправка TCP/UDP по IPv4 и IPv6 (10, 26, 42, 58) |
| Microsoft-Windows-DNS-Client | завершённый DNS-запрос (3008) |

Нужные идентификаторы событий отбираются уже в ядре (фильтр по ID), остальное до агента не доходит. Сессия живёт, пока работает процесс агента; при штатном выходе агент останавливает её (`netupload.Shutdown()`). Если агент упал и оставил сессию, при следующем запуске агент останавливает «чужую» сессию с тем же именем и открывает свою. Сторож замечает, что сессию остановили снаружи (например, `logman stop`), и сборщик сообщает о недоступности и перезапускается.

Сопоставление (`matcher.go`):

- Передача непрерывна: накопитель отправленных байт процессом на адрес одного сервиса сбрасывается только после паузы дольше `window_seconds`.
- Прочитанный файл засчитывается, если чтение произошло не раньше чем за `window_seconds` **до начала** передачи, а сама передача не старше 10 минут.
- Байты, отправленные до чтения файла, для этого чтения не считаются.
- Файл засчитывается, если объём отправки ≥ `размер * (100 - size_tolerance_percent) / 100`. Уверенность `high`, если объём ≥ размера файла, иначе `medium`.
- Несколько файлов за одну передачу делят общий бюджет объёма по убыванию размера.
- Каждое событие чтения сообщается один раз за передачу; новое чтение того же файла считается новой отправкой.
- Сервис определяется по домену из ответов DNS, а если домена нет (DNS поверх HTTPS) — по диапазонам адресов из каталога.

В чтениях учитываются только файлы пользовательских каталогов и внешних томов с разрешённым расширением, размером от `min_file_bytes` до `collectors.artifact.max_bytes` и вне `exclude_paths`.

## 3. Что видно оператору

В консоли, раздел «События», фильтр канала «Сеть»: событие «Сеть → Отправка файла», критичность «Высокая». В карточке события:

| Поле `subject` | Смысл |
|---|---|
| `src_path` | путь прочитанного файла |
| `size_bytes` | размер файла |
| `volume` | тип тома |
| `service`, `service_name` | ключ и название сервиса («Google Drive») |
| `dest_host` | домен, по которому определён сервис (если определён через DNS) |
| `sent_bytes` | сколько процесс отправил |
| `confidence` | `high` — объём покрывает размер файла; `medium` — совпало только с допуском |

Процесс и пользователь указываются как у файловых событий. Если копию снять не удалось, событие всё равно уходит, причина в `labels.artifact_skipped`. Когда воркер находит в копии совпадения с правилами, создаётся инцидент «Отправка файла в сеть: …» с каналом «Сеть».

Служебные события агента: `agent/netupload_unavailable` (источник ETW недоступен; один раз за сбой) и `agent/netupload_dropped` (переполнение собственной очереди сборщика, с числом потерь).

## 4. Настройка

Раздел `collectors.net_upload` конфигурации агента. Отсутствующее или бессмысленное значение заменяется умолчанием. **Пустой список в `extensions`, `exclude_paths`, `services` означает встроенное значение агента.**

| Ключ | Умолчание | Смысл |
|---|---|---|
| `enabled` | `true` | сборщик включён |
| `window_seconds` | 60 (5–600 на сервере) | окно «прочитал → отправил» и допустимая пауза внутри передачи |
| `size_tolerance_percent` | 20 (0–90) | допуск на накладные расходы и сжатие |
| `min_file_bytes` | 1024 | файлы мельче пропускаются |
| `extensions` | pdf, docx, xlsx, pptx, doc, xls, ppt, rtf, txt, csv, zip, 7z, rar | расширения-кандидаты |
| `exclude_paths` | `*\AppData\*`, `?:\Windows\*`, `?:\Program Files*`, `?:\ProgramData\*`, `*\$Recycle.Bin\*` | исключаемые пути (шаблоны) |
| `services` | встроенный каталог (Google Drive, Dropbox, OneDrive/SharePoint, Яндекс.Диск, Облако Mail.ru, Telegram, WhatsApp, веб-почта) | ключ, название, домены, диапазоны адресов |

Максимальный размер файла, скорость и бюджет копирования берутся из `collectors.artifact` (см. `docs/COLLECTORS_MANUAL.md`).

Важно: непустой `services` **заменяет** встроенный каталог целиком, а не дополняет его. Чтобы добавить сервис, перечислите и нужные встроенные записи. Пример добавления корпоративного хранилища:

```json
{
  "collectors": {
    "net_upload": {
      "services": [
        {"key": "gdrive", "name": "Google Drive",
         "domains": ["drive.google.com", "docs.google.com", "drive.usercontent.google.com"]},
        {"key": "corp_share", "name": "Корпоративное хранилище",
         "domains": ["files.example.com"], "cidrs": ["203.0.113.0/24"]}
      ]
    }
  }
}
```

`key` — латиница, цифры и `_`, до 40 символов. Домен совпадает по границе метки: `dropbox.com` и `www.dropbox.com` подходят, `notdropbox.com` нет. Агент подхватывает смену раздела без перезапуска.

## 5. Требования и ограничения

- Только Windows; **агент должен быть запущен от администратора** (сессия ETW). Без прав сборщик не работает, остальные сборщики продолжают работу.
- Если источник ETW не стартует или останавливается, сборщик повторяет попытку с паузой 30 с, удваивая её до 5 минут, и шлёт `agent/netupload_unavailable` один раз за сбой. Если агент не от администратора, он тихо продолжает повторять попытки (только предупреждения в логе).
- DNS поверх HTTPS: домен по DNS не виден, работает запасной путь по диапазонам адресов из каталога; если адрес не опознан, события нет.
- Файл изменён перед отправкой (сжат, переименован, упакован в архив): точное совпадение по размеру не сработает; частично помогают допуск и расширения архивов в `extensions`.
- Файл, который был открыт ещё до старта сессии ETW, не сопоставляется (открытие не было видно).
- Текст сообщений и содержимое форм не читается (подпроект N2).
- Библиотека ETW не показывает счётчик потерянных событий; видны только переполнения собственной очереди (`agent/netupload_dropped`).
- Каталог сервисов стартовый и неполный: сервисы меняют домены и адреса, каталог дополняется конфигурацией.
- Блокировки отправки нет.
- Linux-агенты (в том числе стенд) сборщик не запускают.

## 6. Ручная проверка

Нужна Windows-машина, стенд (`.\stand.cmd up`) и агент, зарегистрированный на нём. **Это обязательный шаг: он закрывает все непроверенные допущения.**

**А. Пробник ETW (от администратора).**

1. `cd agent; go run ./cmd/etwprobe`. В течение 60 секунд откройте сайт в Chrome, откройте и скопируйте `.pdf`, загрузите файл на Google Drive.
2. Если сессия уже существует, пробник остановит её сам; иначе `logman stop "BarysGuard-Probe-Kernel-File" -ets` (и аналогично для других).
3. Сверьте вывод с чек-листом в `ids_windows.go`: идентификаторы событий; имена свойств (`FileObject`, `FileName`, `PID`, `size`, `daddr`, `QueryName`, `QueryResults`); одинаков ли `FileObject` в открытии, чтении и закрытии одного файла; NT-форма пути (`\Device\HarddiskVolumeN\...`); формат `daddr`, `size`, `QueryResults`; приходят ли события чтения с маской ключевых слов `0x20 | 0x80 | 0x100`. При расхождении правится только `ids_windows.go` (и `asAddr`/`asUint` в `props.go`, если иной формат значений; значения библиотека отдаёт строками).

**Б. Браузер (от администратора).**

1. Соберите агент: `cd agent; go build -o C:\BarysGuardTest\barysguard-agent.exe .\cmd\barysguard-agent`.
2. Остановите прежний экземпляр (`Get-Process barysguard-agent`).
3. Запустите: `& C:\BarysGuardTest\barysguard-agent.exe run -data-dir C:\BarysGuardTest\data` (PowerShell от администратора).
4. В Chrome откройте `https://drive.google.com` и загрузите `plan.pdf` (≥ 1 КБ) из «Документов».
5. Через 30–60 секунд в консоли, «События», фильтр «Сеть»: «Отправка файла», путь и сервис «Google Drive».

**В. Жизненный цикл сессии.**

1. Во время работы агента `logman query -ets` показывает сессию `BarysGuard-NetUpload`; после Ctrl+C её нет (`Shutdown`).
2. Завершите агент принудительно (`taskkill /f`) и запустите снова: старт чистый, без ошибки «сессия уже существует».
3. Остановите сессию `logman stop BarysGuard-NetUpload -ets` при работающем агенте: приходит `agent/netupload_unavailable`, затем сборщик сам перезапускает сессию.

**Г. Telegram Desktop.** Отправьте документ из «Документов» в «Избранное»: событие «Отправка файла» с сервисом «Telegram» (определён по диапазону адресов, `dest_host` может быть пуст).

**Д. Отрицательные проверки.** Загрузка картинки `.jpg` и мелкого документа (< 1 КБ) событий не даёт; файл из `AppData` событий не даёт.

## 7. Если событий нет

1. Агент запущен от администратора.
2. В логе агента нет сообщений `сборщик netupload недоступен` и нет события `agent/netupload_unavailable`.
3. Выполнен `etwprobe`, идентификаторы и свойства совпадают с `ids_windows.go` (раздел 6, А).
4. Домен сервиса есть в каталоге (или адрес входит в его диапазоны); при DoH — только диапазоны.
5. Расширение файла входит в `extensions`, путь не попадает под `exclude_paths`.
6. Размер файла в пределах `min_file_bytes` и `collectors.artifact.max_bytes`.
7. Файл не открывался ещё до запуска агента и передан тем же процессом, который его прочитал; он не изменён сильнее допуска перед отправкой.
8. Сессия `BarysGuard-NetUpload` существует (`logman query -ets`).
