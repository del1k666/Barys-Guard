# BarysGuard DLP — план 1B-agent: транспортное ядро Go-агента

**Дата:** 2026-09-15
**Статус:** проектирование завершено
**Предшествующие спеки:** `docs/superpowers/specs/2026-09-08-dlp-transport-core-design.md` (разделы 7–10, 15)
**Контракт:** `api/gateway-v1.yaml` — единственный источник истины

## 1. Цель и границы

Дать конечному хосту работающего агента: он регистрируется по одноразовому токену,
аутентифицируется клиентским сертификатом, сообщает о себе, забирает конфигурацию,
исполняет команды оператора и продлевает сертификат до его истечения.

Сервер для всего перечисленного уже готов (планы 1A и 1B). Этот план замыкает
сквозной контур: до него ни один компонент системы не подключался к серверу по-настоящему.

### 1.1 Что входит

| Возможность | Эндпоинт |
|---|---|
| Получение сертификата CA | `GET /gateway/v1/ca` |
| Регистрация по токену с CSR | `POST /gateway/v1/enroll` |
| Проверка собственной личности | `GET /gateway/v1/whoami` |
| Продление сертификата | `POST /gateway/v1/renew` |
| Сообщение о состоянии, получение команд | `POST /gateway/v1/heartbeat` |
| Получение конфигурации | `GET /gateway/v1/config` |
| Отправка результата команды | `POST /gateway/v1/commands/{id}/result` |

### 1.2 Что не входит

| Что | Куда отнесено | Почему |
|---|---|---|
| Offline-буфер на bbolt | План 1C | Буфер существует ради `POST /events`, а этого эндпоинта на сервере ещё нет. Хранилище, которое некуда разгружать, невозможно проверить по-настоящему — только юнит-тестами на синтетике |
| `POST /events`, `POST /artifacts` | План 1C | Серверная сторона не реализована |
| Защита ключа через DPAPI | Отдельная задача | Требует syscall-обвязки к `CryptProtectData`, проверяемой только на Windows. Интерфейс `platform.Keystore` задаёт точку расширения сразу, поэтому добавление не сломает потребителей |
| Сборщики событий (ФС, буфер обмена, печать) | Подпроект 2 | — |
| Установка службой ОС, MSI, deb/rpm | Подпроект 5 | Агент — обычный долгоиграющий процесс; обёртка в systemd и службу Windows не влияет на транспорт |

Буфер и отправка событий отложены сознательно. Их отсутствие не делает агента
бесполезным: heartbeat, конфигурация и команды работают сквозь весь контур
и проверяются против настоящего сервера.

## 2. Технические решения

| Решение | Значение | Обоснование |
|---|---|---|
| Язык | Go, директива `go 1.23` | Из транспортной спеки. Тулчейн разработки новее и собирает такой модуль без оговорок |
| Путь модуля | `github.com/barysguard/agent` | Отдельный модуль: сервер и агент связаны только контрактом |
| Ключ агента | ECDSA P-256 | Из транспортной спеки, раздел 7.3 |
| Зависимости | `golang.org/x/sys` (BSD-3), `gopkg.in/yaml.v3` только для тестов (MIT) | Всё остальное — стандартная библиотека. GPL и AGPL запрещены проектом |
| Журналирование | `log/slog`, JSON в stdout | Совпадает с форматом сервера, разбирается тем же сборщиком логов |

Отсутствие HTTP-фреймворка и клиентских библиотек намеренно: агент делает семь
запросов известной формы, и `net/http` со `crypto/tls` покрывают это полностью.
Каждая зависимость на конечном хосте — это ещё одна поверхность обновления
на тысячах машин.

## 3. Структура модуля

```
agent/
├── go.mod
├── cmd/barysguard-agent/
│   └── main.go              разбор подкоманд, сигналы, коды возврата
└── internal/
    ├── config/              локальные настройки и раскладка каталогов
    ├── hostfacts/           machine_id, hostname, os, os_version, arch
    ├── keystore/            ключ, сертификат, CSR, срок действия
    ├── platform/            build tags windows/linux: права доступа, machine_id
    ├── transport/           mTLS-клиент: единственный обладатель знания об HTTP
    └── runner/              расписание, откат, диспетчер команд
```

Главная граница: **`transport` знает про HTTP и ничего — про расписание;
`runner` знает про расписание и ничего — про HTTP.** Именно она позволит в плане 1C
вставить отправку событий, не трогая цикл heartbeat, и заменить опрос на long-polling,
не переписывая обработчики команд.

Вторая граница — `platform`. Всё, что различается между Windows и Linux, живёт
за одним интерфейсом и нигде больше:

```go
// platform.Guard закрывает файлы ключей от посторонних и подтверждает,
// что они закрыты. Проверка нужна не меньше установки: ключ, оставшийся
// читаемым после ручного копирования каталога, — это скомпрометированный ключ.
type Guard interface {
    SecureDir(path string) error
    SecureFile(path string) error
    VerifySecure(path string) error
    MachineID() (string, error)
}
```

## 4. Доверие к серверу и бутстрап

Это место, где транспортная спека оставляет пробел, и закрыть его надо явно.

Чтобы выполнить `POST /enroll` по TLS, агент обязан уже кому-то доверять — но
собственного сертификата у него ещё нет. При этом `GET /ca` отдаёт внутренний CA,
подписывающий **агентские** сертификаты, и он не обязан совпадать с TLS-сертификатом,
которым nginx представляется клиенту.

**Решение:** CA поставляется вместе с дистрибутивом агента, как и говорит
транспортная спека в разделе 7.1.

| Режим | Флаг | Поведение |
|---|---|---|
| Основной | `--ca-file <путь>` | CA берётся из дистрибутива и помещается в `RootCAs`. Сеть в установлении доверия не участвует |
| Запасной | `--ca-pin <sha256>` | CA забирается через `GET /ca` и принимается, только если SHA-256 его DER совпал с отпечатком |

Молчаливого trust-on-first-use нет и не будет. Скачать CA по непроверенному каналу
и немедленно начать ему доверять — это ровно тот перехват, против которого
и вводится mTLS. Если не задан ни `--ca-file`, ни `--ca-pin`, команда `enroll`
завершается ошибкой, а не выбирает что-нибудь на своё усмотрение.

## 5. Раскладка на диске

```
<data-dir>/
├── agent.json        локальные настройки: server_url, log_level
├── state.json        agent_id, config_version, последний документ конфигурации
└── pki/
    ├── ca.crt        CA, которому доверяет агент
    ├── agent.crt     сертификат агента
    └── agent.key     приватный ключ, доступ ограничен
```

Каталог по умолчанию: `%ProgramData%\BarysGuard` на Windows,
`/var/lib/barysguard` на Linux. Переопределяется флагом `--data-dir`.

Настройки и состояние разделены намеренно: `agent.json` заполняет установщик или
оператор, `state.json` пишет сам агент. Смешать их означало бы, что переустановка
с готовым файлом настроек затирает заработанную личность агента — либо наоборот,
что агент правит то, что ему дал оператор.

Документ конфигурации кешируется в `state.json` вместе с его версией. Без кеша
`If-None-Match` бессмысленен: после перезапуска агент не знал бы, с чем сравнивать,
и тянул бы полный документ при каждом старте.

### 5.1 Права доступа

| Платформа | Каталог `pki/` | `agent.key` |
|---|---|---|
| Linux | `0700`, владелец процесса | `0600` |
| Windows | DACL: только `SYSTEM` и `Administrators`, наследование отключено | то же |

Агент **отказывается стартовать**, если ключ доступен посторонним, — так же,
как это делает `ssh`. Ключ, который прочитал кто угодно, уже не является
доказательством личности, и продолжать работу, делая вид, что является, хуже,
чем остановиться.

### 5.2 Атомарность записи

Сертификат и ключ записываются во временный файл рядом и переименовываются
поверх целевого. Обрыв питания посреди продления иначе оставляет агента
с ключом от одного сертификата и телом другого — состояние, из которого
он не выйдет без переустановки.

## 6. Факты хоста

Поля соответствуют схеме `HostFacts` контракта.

| Поле | Windows | Linux |
|---|---|---|
| `machine_id` | `HKLM\SOFTWARE\Microsoft\Cryptography\MachineGuid` | `/etc/machine-id`, при отсутствии — `/var/lib/dbus/machine-id` |
| `hostname` | `os.Hostname()` | `os.Hostname()` |
| `os` | `"windows"` | `"linux"` |
| `os_version` | версия сборки из `RtlGetVersion` | `PRETTY_NAME` из `/etc/os-release` |
| `arch` | `runtime.GOARCH` | `runtime.GOARCH` |
| `agent_version` | константа сборки, задаётся через `-ldflags` | то же |

Если `machine_id` получить не удалось, `enroll` завершается ошибкой. Придумать
идентификатор на лету было бы худшим из вариантов: сервер отсеивает дубли
именно по нему, и случайное значение при каждом запуске превратило бы
один хост в россыпь агентов-призраков.

## 7. Транспорт

Единственный тип, знающий про HTTP:

```go
type Client struct { /* http.Client с tls.Config */ }

func (c *Client) CA(ctx context.Context) ([]byte, error)
func (c *Client) Enroll(ctx context.Context, req EnrollRequest) (EnrollResponse, error)
func (c *Client) Renew(ctx context.Context, csrPEM string) (RenewResponse, error)
func (c *Client) Heartbeat(ctx context.Context, req HeartbeatRequest) (HeartbeatResponse, error)
func (c *Client) Config(ctx context.Context, etag string) (ConfigResponse, bool, error)
func (c *Client) CommandResult(ctx context.Context, id string, req CommandResultRequest) error
```

`Config` возвращает вторым значением признак «не изменилось» — ответ `304`
не является ошибкой и не должен превращаться в неё по дороге.

Клиент строится в двух видах: **бутстрапный** (только `RootCAs`, для `GET /ca`
и `POST /enroll`) и **взаимный** (`RootCAs` плюс `Certificates` — клиентский
сертификат, для всего остального). Один тип с необязательным сертификатом
привёл бы к тому, что забытая настройка молча даёт анонимный запрос,
а сервер отвечает `403` без объяснения причины.

### 7.1 Соответствие контракту

Структуры пишутся руками, но их соответствие контракту проверяется тестом:
он читает `api/gateway-v1.yaml` и сверяет имена обязательных полей каждой
схемы с тегами `json` соответствующей структуры Go.

Это дешевле генерации кода из OpenAPI и ловит ровно то расхождение, которое
реально случается: поле переименовали на сервере, агент продолжает слать старое
имя, сервер молча подставляет значение по умолчанию. Такую ошибку находят
не в тестах, а на внедрении.

## 8. Цикл работы

Подкоманды одного бинаря:

| Команда | Назначение |
|---|---|
| `enroll` | Однократная регистрация. Требует `--token` и CA |
| `run` | Долгоиграющий цикл heartbeat |
| `status` | Локальная диагностика: `agent_id`, срок сертификата, версия конфигурации |

### 8.1 `enroll`

1. Загрузить CA (из `--ca-file` либо по `GET /ca` с проверкой `--ca-pin`).
2. Сгенерировать ключ ECDSA P-256 и CSR. Субъект CSR произвольный — сервер
   его игнорирует и формирует собственный.
3. Собрать факты хоста.
4. `POST /enroll` с токеном, CSR и фактами.
5. Сохранить `agent_id`, сертификат, CA и ключ; выставить и проверить права.

Повторный `enroll` при уже существующем сертификате отклоняется, если не задан
`--force`. Затереть действующую личность агента одной неосторожной командой
не должно быть возможно.

### 8.2 `run`

Один проход цикла:

1. `POST /heartbeat` с `agent_version`, `config_version` из состояния,
   `sent_at` по часам агента, `buffered_events: 0`, `buffer_bytes: 0`.
2. Применить `heartbeat_interval_seconds` из ответа к следующему тику.
3. Если `config_version` в ответе отличается от сохранённой — `GET /config`
   с `If-None-Match`; при `200` сохранить документ и версию.
4. Исполнить пришедшие команды.
5. Отправить результат по каждой: `POST /commands/{id}/result`.
6. Проверить срок сертификата, при необходимости продлить.

Поля `buffered_events` и `buffer_bytes` присутствуют в контракте и передаются
нулями: буфера в этом плане нет. Опустить их нельзя — контракт задаёт форму
запроса, и агент обязан ей соответствовать независимо от своей полноты.

### 8.3 Джиттер установившегося интервала

К интервалу из ответа добавляется случайное отклонение до ±10%.

Без него флот, развёрнутый одной волной, остаётся синхронным навсегда: все
агенты зарегистрировались в одну минуту и с тех пор стучатся в сервер
одновременно. Откат при ошибках эту синхронность не разводит — он включается
только при сбоях, а описанная волна возникает при штатной работе.

## 9. Обработка ошибок

| Ситуация | Поведение |
|---|---|
| `403` | Сертификат отозван либо не признан. Остановиться, записать причину, выйти с кодом `2`. Повторы бессмысленны и лишь добавляют нагрузки |
| `429` | Ждать столько, сколько указано в `Retry-After`; собственный откат при этом не применяется |
| `5xx`, обрыв соединения, таймаут | Экспоненциальный откат с полным джиттером: база 1 с, потолок 300 с |
| `304` на `/config` | Сохранённый документ остаётся как есть |
| `400` на результат команды | Команда закрывается локально: повтор с тем же телом даст тот же ответ |
| Команда завершилась ошибкой | `status: "failed"`, текст ошибки в `result`. Молчание оставило бы команду висеть до истечения TTL |

Откат — с **полным** джиттером (`random(0, min(cap, base·2^n))`), а не с половинным.
Пять тысяч агентов, переподключающихся после перезапуска сервера, при неполном
джиттере сохраняют форму волны и укладывают сервер повторно.

Отдельный код возврата `2` для `403` нужен супервизору: `systemd` с
`RestartPreventExitStatus=2` не станет бесконечно поднимать агента, чей
сертификат отозвали намеренно.

### 9.1 Неотправленные результаты

Если `POST /commands/{id}/result` не прошёл, результат остаётся в очереди
в памяти и повторяется на следующем проходе цикла. Очередь ограничена сотней
записей: команда, чей результат не удалось отдать за сотню циклов,
всё равно истечёт на сервере.

Перезапуск агента такую очередь теряет. Это осознанное ограничение плана:
долговечная очередь — это тот же bbolt, что и offline-буфер, и делать
его дважды незачем. Сервер переводит невыполненные команды в `expired`
по TTL, поэтому потеря результата не оставляет команду висеть вечно.

## 10. Команды

Диспетчер — отображение типа команды на обработчик, отделённое от цикла:

```go
type Handler func(ctx context.Context, payload map[string]any) (map[string]any, error)
```

| Тип | Результат |
|---|---|
| `ping` | `{"pong": true, "agent_time": "<RFC3339>"}` |
| `refresh_config` | Принудительный `GET /config` без `If-None-Match`; `{"config_version": N}` |
| `collect_diagnostics` | `agent_version`, `os`, `arch`, `uptime_seconds`, `cert_not_after`, `last_heartbeat_at`, `config_version` |

Неизвестный тип команды — это `failed` с внятным текстом, а не падение цикла.
Сервер новее агента вправе прислать команду, о которой агент не знает; правило
совместимости из транспортной спеки (агент версии N работает с сервером N и N+1)
требует именно такого поведения.

Результат сериализуется и, если превысил 64 КБ (`MAX_RESULT_BYTES` сервера),
заменяется на пометку об усечении. Диагностика не является каналом передачи
артефактов — для этого в плане 1C предусмотрен `POST /artifacts`.

## 11. Продление сертификата

Продление запускается, когда истекло **2/3 срока** с момента выпуска —
60 суток из 90, как задаёт транспортная спека.

Проверка идёт по полям `NotBefore` и `NotAfter` самого сертификата, а не по
записанной дате: файл могли восстановить из резервной копии, и сохранённая
отметка соврала бы.

При продлении генерируется **новая** ключевая пара. Переиспользование старого
ключа означало бы, что компрометация, случившаяся однажды, переживает все
последующие продления.

Порядок записи: получить новый сертификат → записать новый ключ и сертификат
во временные файлы → переименовать оба поверх целевых. Неудача продления
не трогает действующие файлы: у агента остаётся рабочий сертификат
и запас в 30 суток на повторные попытки.

## 12. Тестирование

Разработка по TDD: тест предшествует коду.

| Уровень | Что проверяется | Когда идёт |
|---|---|---|
| Юнит | Факты хоста, CSR и разбор сертификата, откат с инжектированным генератором случайных чисел, диспетчер команд, усечение результата | Всегда |
| Права доступа | `0600`/`0700` на Linux, DACL на Windows, отказ стартовать при слабых правах | Всегда, на своей платформе |
| Интеграция транспорта | `httptest` с настоящим TLS: CA выпускается в тесте, сервер требует клиентский сертификат | Всегда |
| Контракт | Имена полей структур против `api/gateway-v1.yaml` | Всегда |
| Сквозной | Настоящий бинарь против настоящего сервера | Build tag `e2e`, при поднятом Docker |

Генератор случайных чисел в откате инжектируется. Иначе джиттер непроверяем:
тест либо принимает любой результат, либо становится хлопающим.

Интеграционные тесты поднимают `httptest` с `tls.Config{ClientAuth:
RequireAndVerifyClientCert}`. Это принципиально: проверяется, что клиент
**действительно** предъявляет сертификат, а не что мы так считаем. Мок,
принимающий любой запрос, подтвердил бы работоспособность неработающего агента.

Сквозной тест под тегом отделён потому, что требует Docker и живого сервера.
Делать его обязательным для каждого прогона значило бы остановить разработку
всякий раз, когда Docker не поднят.

## 13. Критерии готовности

1. `go vet` и `go test ./...` чисты; сборка проходит для `GOOS=windows` и `GOOS=linux`.
2. Агент регистрируется по токену и получает сертификат от настоящего сервера.
3. Heartbeat обновляет запись агента; расхождение часов фиксируется сервером.
4. Команда, поставленная оператором, доезжает до агента, исполняется и её
   результат виден через операторский API.
5. Правка конфигурации на сервере меняет версию, и агент забирает новый документ.
6. Совпавшая версия конфигурации даёт `304` и не тянет документ повторно.
7. Отзыв сертификата немедленно прекращает обслуживание: агент получает `403`
   и завершается с кодом `2`.
8. Обрыв связи не роняет агента: он повторяет попытки с нарастающей паузой
   и продолжает работу после восстановления сети.

## 14. Открытые вопросы, вынесенные за план

| Вопрос | Когда решается |
|---|---|
| DPAPI для ключа на Windows | Отдельная задача; точка расширения заложена в `platform.Guard` |
| Долговечная очередь результатов команд | План 1C, вместе с bbolt-буфером |
| Установка службой ОС и обновление флота | Подпроект 5 |
| Защита процесса агента от завершения | Требует драйвера; компенсируется тем, что пропавшие heartbeat сами являются событием |
