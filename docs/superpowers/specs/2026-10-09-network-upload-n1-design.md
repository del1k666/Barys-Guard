# BarysGuard DLP — отправка файлов в сеть: связка «файл → процесс → сеть» (подпроект N1)

- **Дата:** 2026-10-09
- **Статус:** проект, ждёт одобрения
- **Область:** сборщик агента под Windows, который находит отправку документа во внешний сервис (облачное хранилище, мессенджер, почта) по связке «процесс прочитал файл и отправил на адрес сервиса не меньше байт, чем размер файла», снимает зашифрованную копию файла и шлёт событие `network/upload`. Дальше работает готовый конвейер: артефакт, воркер инспекции, правила, инцидент.
- **Опора:** `2026-10-05-collectors-files-usb-design.md` (сборщики, `Attributor`, очередь событий), `2026-10-05-artifact-upload-design.md` (копии файлов и загрузка), `2026-10-06-dlp-worker-design.md` (инспекция), `2026-10-06-rules-editor-design.md` (правила).

**Критерий завершения:** на Windows-машине агент, запущенный от администратора, при загрузке документа (pdf, docx и т. д.) из браузера или десктопного клиента в сервис из каталога присылает событие `network/upload` с артефактом; воркер проверяет содержимое правилами, и в консоли появляется инцидент с каналом «Сеть»; агент без прав или без ETW продолжает работу остальных сборщиков; Docker-стенд (агенты на Linux) работает без изменений.

---

## 1. Место в общей задаче

Полный контроль исходящего трафика разбит на три независимых подпроекта (по одной спецификации на каждый):

| № | Подпроект | Что даёт |
|---|---|---|
| **N1** | **этот документ:** файл → процесс → сеть | покрытие всех приложений, включая закреплённые сертификаты, для передачи файлов |
| N2 | локальный прокси с подменой TLS | тела запросов и текст форм и чатов у приложений без закрепления сертификатов |
| N3 | внутрипроцессный перехват | текст в приложениях с закреплением сертификатов; только под конкретные приложения, если N1+N2 не хватит |

Порядок N1 → N2 → N3. N2 и N3 в этом документе не проектируются.

## 2. Границы

### 2.1 Что входит

| Часть | Содержание |
|---|---|
| Агент | сборщик `netupload` (Windows): сессия ETW, окно прочитанных документов, сопоставление адресов с доменами, решающий узел, снятие копии через существующий `artifacts`, событие |
| Конфигурация | раздел `collectors.netupload` в документе конфигурации агента (сервер и агент), каталог сервисов |
| Сервер | проверка `subject` канала `network` / действия `upload`; подписи канала и действия в консоли |
| Документация | описание сборщика, ограничения, ручная проверка |

### 2.2 Что не входит

| Не делаем | Почему |
|---|---|
| Блокировка отправки | usermode видит факт после начала отправки; блокировка требует драйвера ядра, отдельный проект |
| Чтение текста сообщений и содержимого форм | подпроекты N2 и N3 |
| Расшифровка трафика | подпроекты N2 и N3 |
| Редактор каталога сервисов в консоли | каталог приходит в конфигурации агента; редактор можно добавить позже |
| Linux и macOS | на других платформах сборщик возвращает пустую реализацию |
| Порт для мобильных устройств | вне проекта |

## 3. Устройство

```
ETW: чтение файлов ─┐
ETW: отправка сети ─┼─▶ reads · dnsmap ─▶ matcher ─▶ artifacts (копия) + events.Queue
ETW: DNS ───────────┘                                    │
                                                         ▼
                                   сервер → воркер → правила → инцидент
```

Все Windows-специфичные вызовы лежат за интерфейсами и в файлах `*_windows.go`; на остальных платформах `*_other.go` возвращают пустую реализацию, и агент (в том числе в Docker-стенде) собирается и работает без сборщика. Остальная логика переносима и покрывается обычными юнит-тестами.

### 3.1 Компоненты

| Компонент | Что делает |
|---|---|
| `etwsession` | открывает сессию ETW и отдаёт типизированные события: чтение файла (процесс, путь), отправка по сети (процесс, адрес, байты), ответ DNS (домен → адреса). Интерфейс над платформенной реализацией |
| `reads` | для каждого процесса хранит короткое окно последних прочитанных документов. Фильтр на входе: пользовательские каталоги и внешние тома, разрешённые расширения, размер не меньше `min_file_bytes` и не больше лимита `collectors.artifact.max_bytes`, исключённые пути отброшены. Память ограничена числом процессов и записей |
| `dnsmap` | кэш «адрес → домен» из событий DNS с учётом времени жизни записи; по каталогу определяет сервис адреса; запасной путь по диапазонам адресов из каталога |
| `matcher` | решающий узел: на событие отправки к адресу сервиса ищет в окне процесса документы, чей размер покрыт объёмом отправки с допуском; для каждого найденного снимает копию и ставит событие |

## 4. Событие

Канал `network`, действие `upload`. Поля `subject`:

| Поле | Смысл |
|---|---|
| `src_path` | путь прочитанного файла; обязательное, непустое |
| `size_bytes` | размер файла |
| `volume` | тип тома, как у файловых событий |
| `service` | ключ сервиса из каталога (`gdrive`, `telegram`, …) |
| `dest_host` | домен, по которому определён сервис, если определён через DNS |
| `sent_bytes` | сколько процесс отправил в окне |
| `confidence` | `high` — объём отправки покрывает размер файла; `medium` — совпало только с учётом допуска |

Процесс и пользователь заполняются через `Attributor`, как у файловых событий. Хеш и артефакт — в `artifact.sha256`, загрузка содержимого идёт существующим воркером агента; повторная отправка того же содержимого не передаётся по сети (ответ `exists`). Критичность события — `high`. Если копию снять не удалось (слишком большой файл, исчез, лимит скорости), событие всё равно уходит, причина в `labels.artifact_skipped`.

## 5. Конфигурация

Раздел `collectors.netupload`. Отсутствующее или бессмысленное значение заменяется умолчанием.

| Ключ | Умолчание | Смысл |
|---|---|---|
| `enabled` | `true` | сборщик включён |
| `window_seconds` | 60 | окно «прочитал → отправил» |
| `size_tolerance_percent` | 20 | допуск на накладные расходы |
| `min_file_bytes` | 1024 | мельче файлы пропускаются |
| `extensions` | pdf, docx, xlsx, pptx, doc, xls, ppt, rtf, txt, csv, zip, 7z, rar | кандидаты |
| `paths_exclude` | системные каталоги, кэши браузеров и мессенджеров | исключения |
| `services` | встроенный каталог (Google Drive, Dropbox, OneDrive, Яндекс.Диск, Mail.ru Облако, Telegram, WhatsApp, веб-почта) | ключ, название, домены, при необходимости диапазоны адресов |
| `process_hints` | браузеры и мессенджеры | процессы, которым доверие выше (влияет на `confidence`) |

Лимит размера, скорость и бюджет копирования берутся из существующего `collectors.artifact`.

## 6. Нагрузка и надёжность

- События чтения файлов — самый шумный поток; фильтрация идёт в обработчике до выделения памяти: расширение, затем путь, затем запись в окно процесса. Размер файла определяется один раз.
- Число процессов и записей в окнах ограничено, старые вытесняются. Окна живут не дольше `window_seconds`.
- Сессия ETW использует буферы ограниченного размера. Потеря событий (счётчик ETW) отражается редким событием `agent/netupload_dropped` с числом потерь.
- Сопоставление запускается только при отправке на адрес сервиса из каталога; остальные сетевые события отбрасываются одной проверкой по таблице.
- Нет прав или ETW недоступен: сборщик не стартует, агент шлёт `agent/netupload_unavailable` и продолжает работу остальных сборщиков.
- Файл исчез или изменился до снятия копии: хеш и копия берутся по фактически снятому; при неудаче событие уходит с `artifact_skipped`.
- Дедупликация по ключу «процесс + файл + сервис» в окне, чтобы разбитая на куски загрузка не давала десяток событий.
- Один процесс отправил несколько файлов: сопоставление по убыванию соответствия размеру, каждому файлу своё событие, пока объём отправки не исчерпан.
- Приложение использует DNS поверх HTTPS (DoH): домен по DNS не определяется, работает запасной путь по диапазонам адресов из каталога; если адрес не опознан, события нет. Это известный пробел, он описывается в документации.
- Файл изменён перед отправкой (сжат, переименован, упакован в архив): точное совпадение по размеру не сработает; частично помогают допуск и расширение архивов в `extensions`.

## 7. Сервер

- `server/barysguard/services/event_subjects.py`: ветка для `Channel.NETWORK`, действие `upload`, непустой `src_path`, проверка `volume`, неотрицательные целые `size_bytes` и `sent_bytes` (если есть), остальные поля необязательны; лишние поля допускаются.
- Воркер инспекции не меняется: событие с артефактом попадает в очередь тем же путём.
- Консоль: подписи канала «Сеть» и действия «Отправка файла»; в карточке события видны сервис, домен и процесс.
- Новых таблиц нет.

## 8. Приватность

На сервер уходят путь, сервис, домен из каталога и размеры; содержимое сетевого трафика не читается. Содержимое файла — только зашифрованный артефакт, как у USB. Домен каталога не раскрывает конкретную страницу или канал мессенджера.

## 9. Тестирование

- Переносимая логика (`reads`, `dnsmap`, `matcher`, разбор конфигурации, фильтры) — юнит-тесты на искусственных потоках событий: нормальная отправка, чужой процесс, разбитая загрузка, дубли, переполнение окон, пропуск по расширению и пути, несколько файлов за раз, адрес вне каталога, DoH с запасным путём.
- Windows-часть `etwsession` — за интерфейсом; ручная проверка с настоящим браузером и десктопным клиентом (сценарий в документации).
- Сервер: тесты проверки `subject` канала `network`; сквозной тест «событие с артефактом → воркер → инцидент с каналом network»; контракт OpenAPI, если он затронут.
- `go vet`, сборка под Linux (`GOOS=linux go build ./...`) и под Windows остаются зелёными.

## 10. Порядок работ

1. Сервер: проверка `subject`, подписи в консоли (быстрая часть, проверяется тестами).
2. Агент: конфигурация, `reads`, `dnsmap`, `matcher` на искусственных событиях.
3. Агент: `etwsession` (Windows) и подключение к фабрике сборщиков.
4. Снятие копии через `artifacts` и отправка события.
5. Документация, ручная проверка на настоящем агенте.

## 11. Открытые вопросы для плана

- Конкретная библиотека ETW для Go (или собственные вызовы Windows API) — выбор делается в плане по результату короткого испытания: нужен список провайдеров Kernel-File, Kernel-Network и DNS-Client и приемлемая нагрузка.
- Точный состав встроенного каталога сервисов (домены и диапазоны) — уточняется при реализации по проверенным данным.
