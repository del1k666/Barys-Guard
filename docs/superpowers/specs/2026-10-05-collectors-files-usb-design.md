# BarysGuard DLP — сборщики «Файлы и USB» (подпроект 2b-1)

- **Дата:** 2026-10-05
- **Статус:** реализовано (подпроект 2b-1)
- **Область:** первые реальные сборщики агента под Windows: подключение и отключение внешних носителей, события файловой системы в наблюдаемых папках и на внешних томах, хеширование, привязка к пользователю и процессу, сопоставление копирования. Буфер обмена, печать, сеть, содержимое файлов (`/artifacts`) и инспекция вне области.
- **Опора:** разделы 4, 5 и 9 основной спеки `2026-09-08-dlp-transport-core-design.md`; конвейер событий `2026-10-05-event-pipeline-design.md` (подпроект 2a).

**Критерий завершения:** на Windows-машине агент, запущенный от администратора, присылает на сервер события при подключении флешки (`usb/mount`), при записи файла на неё (`file/create`, при совпадении с недавно виденным файлом — `file/copy` с `src_path`), при изменении и удалении файлов в наблюдаемых папках; события видны в `GET /api/v1/events` с пользователем и (когда его удалось определить) процессом; `.\test.cmd` зелёный; Docker-стенд (агенты на Linux) продолжает работать без изменений.

## 2. Устройство

```
              ┌────────────── volumes (один опрос томов) ──────────────┐
              │  Snapshot() · Watch(ctx) → изменения: Mounted/Unmounted │
              └───────────────┬────────────────────────┬───────────────┘
                              │                        │
                       collector usb             collector filewatch
                  usb/mount · usb/unmount   ┌──────────┴───────────┐
                                            │ watchers (по корню)  │
                                            │ debounce → hasher    │
                                            │ hashindex · actor ·  │
                                            │ attributor           │
                                            └──────────┬───────────┘
                                                       ▼
                                             events.Queue → буфер → сервер
```

Все Windows-специфичные вызовы лежат за интерфейсами и в файлах `*_windows.go`; на остальных платформах `*_other.go` возвращают пустую реализацию, и агент (в том числе в Docker-стенде) собирается и работает без этих сборщиков. Переносимая логика (склейка событий, индекс хешей, классификация томов, разбор конфигурации) покрывается обычными юнит-тестами без Windows.

## 3. Пакет `volumes`

```go
type Volume struct {
    DriveLetter string // "E:"
    Serial      string // серийный номер тома, hex
    Label, FS   string
    SizeBytes   int64
    Type        string // fixed | removable | network | unknown
    Bus         string // usb | other | unknown
    Vendor, Product, DeviceSerial string
}

type Provider interface{ Snapshot() ([]Volume, error) }

type Change struct { Mounted bool; Volume Volume }

func Watch(ctx context.Context, p Provider, interval time.Duration) <-chan Change
```

- **Windows-реализация `Snapshot`:** `GetLogicalDrives` → для каждой буквы `GetDriveType`, `GetVolumeInformation` (метка, серийный номер, ФС), размер через `GetDiskFreeSpaceEx`; шина и производитель — `DeviceIoControl(IOCTL_STORAGE_QUERY_PROPERTY)` по открытому без прав на чтение `\\.\E:`.
- **Внешним считается том с `Bus == usb`**, а не только `DRIVE_REMOVABLE`: внешние жёсткие диски Windows показывает как фиксированные. Итоговый `Type` для таких томов — `removable`.
- **Опрос раз в 2 секунды** (`collectors.usb.poll_seconds`). Событие устройства Windows (`WM_DEVICECHANGE`) требует скрытого окна и цикла сообщений и не даёт выигрыша, который стоил бы этой сложности для аудита.
- **`Watch`** сравнивает снимки по паре «буква + серийный номер» (смена носителя в той же букве — это unmount и mount). Первый снимок порождает `Mounted` для уже подключённых носителей: агент, запущенный с вставленной флешкой, должен её увидеть.
- Несколько подписчиков (`usb` и `filewatch`) получают один и тот же поток через небольшой хаб: опрашивается один раз.

## 4. Сборщик `usb`

События канала `usb`, `subject` по схеме раздела 7:

| `action` | Когда | `severity_hint` |
|---|---|---|
| `mount` | появился том с `Bus == usb` | `low` |
| `unmount` | том исчез | `info` |

Тома без шины USB (внутренние диски, сетевые) событий канала `usb` не порождают. `process` и `actor` не заполняются: подключение устройства — действие системы; пользователь — активная консольная сессия (см. §6).

## 5. Сборщик `filewatch`

### 5.1 Что наблюдается

- **Наблюдаемые папки** из `collectors.file_watch.paths`. Значение по умолчанию — `["%USERS%\\Documents", "%USERS%\\Desktop", "%USERS%\\Downloads"]`, где `%USERS%` раскрывается в каталог каждого профиля в `%SystemDrive%\Users`, кроме `Public`, `Default`, `Default User`, `All Users` и профилей без перечисленных папок.
- **Корень каждого внешнего тома** (`Type == removable`) — добавляется при `Mounted`, снимается при `Unmounted`.
- Наблюдение рекурсивное. Агент не наблюдает собственный рабочий каталог и путь из `exclude`.

### 5.2 Источник событий

Один наблюдатель на корень: `CreateFile(FILE_FLAG_BACKUP_SEMANTICS)` и блокирующий цикл `ReadDirectoryChangesW` (буфер 64 КиБ, фильтр: имя файла, имя каталога, размер, время записи). Остановка — `CancelIoEx` и закрытие дескриптора.

- Переполнение буфера (возврат 0 байт) порождает `agent/watch_overflow` с путём корня; повторного сканирования нет — потерянные изменения в аудите принимаются, но не скрываются.
- Пара `RENAMED_OLD_NAME` и `RENAMED_NEW_NAME` собирается в одно событие `file/rename` с `old_path` и `dst_path`. Перенос между томами Windows сообщает как удаление и создание.

### 5.3 Склейка и стабилизация (`debounce`)

Одна копия файла порождает десятки уведомлений. На каждый путь ведётся состояние; событие выходит, когда файл **стабилен**: нет новых уведомлений `collectors.file_watch.stable_ms` (по умолчанию 1500) мс, но не позже `max_wait_ms` (30000) с первого. Итоговое действие: `create`, если было создание; иначе `modify`; `delete`, если файл исчез; `rename` для переименований. Создание и удаление за один период склейки (временный файл) событий не порождает. Каталоги событий не порождают: они отсеиваются при хешировании (открытие каталога как файла). Исключение — удаление, где тип уже неизвестен: удаление каталога приходит как `file/delete`.

### 5.4 Хеширование

Для стабильного файла размером не более `max_hash_bytes` (по умолчанию 256 МиБ) считается SHA-256 потоком, файл открывается с общим доступом на чтение. При нарушении совместного доступа — повторы с нарастающей паузой до конца окна `max_wait_ms`; если файл так и не открылся, событие уходит без `artifact` и с `labels.hash = "unavailable"`. Для файла больше предела хеш не считается: событие уходит без `artifact`, с `labels.hash = "skipped_size"` и размером в `subject.size_bytes`. Контракт 2a допускает `artifact` только с хешем, поэтому поле опускается целиком.

### 5.5 Сопоставление копирования (`hashindex`)

Индекс «`sha256 + size` → последний известный путь в наблюдаемой (не внешней) папке»: ограничен 10 000 записей, срок 24 часа, вытеснение по давности. Индекс пополняется событиями `create` и `modify` из наблюдаемых папок с вычисленным хешем.

Любая запись на внешний том (`create` и `modify` на съёмном томе) получает `action = "copy"` и `severity_hint = "high"`: правилам DLP нужно действие «файл отправлен на USB». Если хеш файла есть в индексе, добавляется `subject.src_path`; иначе `src_path` нет, а `labels.source = "unknown"`. События в наблюдаемых папках — `info`.

Ограничение, которое надо знать: источник копирования, которого агент не видел в наблюдаемых папках (он лежит вне них, либо изменён до запуска агента, либо файл меньше 1 КиБ), остаётся неизвестным. Само событие **не теряется**.

### 5.6 Пользователь и процесс

- **`actor`:** владелец файла (`GetNamedSecurityInfo`, `LookupAccountSid`). Если владелец — `SYSTEM`, `Administrators` или `TrustedInstaller`, берётся пользователь активной консольной сессии (`WTSGetActiveConsoleSessionId`, `WTSQuerySessionInformation`); поля: `user_sid`, `user_name` (формат `ДОМЕН\имя`), `session_id`. Если определить нельзя, `actor` пуст.
- **`process`** (интерфейс `Attributor`), только для событий на внешних томах (Restart Manager дорог, а интересны именно они): реализация A — Restart Manager (`RmStartSession`, `RmRegisterResources`, `RmGetList`) по пути файла, пока он ещё открыт копирующим процессом; поля `pid`, `path` (`QueryFullProcessImageName`). Не определено — `process` пуст и `labels.process = "unknown"`. Интерфейс допускает замену реализацией на ETW без изменений сборщика.

### 5.6.1 Защита от шторма

Не более `collectors.file_watch.max_events_per_second` (по умолчанию 200) событий в секунду из сборщика; ограничитель стоит до хеширования. Отброшенное считает сам сборщик и сообщает событием `agent/events_dropped` со `subject.component = "filewatch"` и `subject.count`. Каталог с массовыми изменениями (распаковка архива) не должен останавливать агента.

## 6. Конфигурация

Раздел `collectors` в документе конфигурации агента (`AgentConfigDocument`, `extra="forbid"`):

```json
"collectors": {
  "usb":        { "enabled": true, "poll_seconds": 2 },
  "file_watch": {
    "enabled": true,
    "paths": ["%USERS%\\Documents", "%USERS%\\Desktop", "%USERS%\\Downloads"],
    "exclude": ["*\\~$*", "*.tmp", "*.crdownload", "*\\AppData\\*"],
    "stable_ms": 1500, "max_wait_ms": 30000,
    "max_hash_bytes": 268435456, "max_events_per_second": 200
  }
}
```

Границы значений проверяет сервер (например, `poll_seconds` 1–60, `stable_ms` 200–60000, `max_hash_bytes` 1 МиБ – 4 ГиБ, `max_events_per_second` 1–10000). Шаблоны `exclude` сопоставляются с полным путём без учёта регистра (`path.Match` по компонентам в стиле Windows).

**Применение.** Сборщики строятся фабрикой `func(document map[string]any) []events.Collector`. Агент запускает группу при старте и **перезапускает её при смене версии конфигурации**: группа останавливается, дожидается возврата, собирается заново из нового документа. Сборщик `lifecycle` от конфигурации не зависит и не перезапускается. Перезапуск сопровождается событием `agent/config_applied` (механизм 2a).

На платформах без поддержки фабрика возвращает пустой список: Docker-агенты работают только с `lifecycle`.

## 7. Контракт событий

### 7.1 Канал `file`

`action`: `create | modify | rename | delete | copy`.

```json
"subject": {
  "dst_path": "E:\\отчёт.xlsx",
  "src_path": "C:\\Users\\ivanov\\Documents\\отчёт.xlsx",
  "old_path": "…",
  "size_bytes": 184320,
  "volume": { "type": "removable", "serial": "0781-5583", "label": "KINGSTON", "fs": "NTFS" }
},
"artifact": { "sha256": "a3f9…", "size": 184320, "uploaded": false }
```

- `dst_path` обязателен всегда (для `delete` — путь удалённого файла); `src_path` — только для `copy`, и не всегда (источник может быть неизвестен); `old_path` — только для `rename`.
- `volume.type` — `fixed | removable | network | unknown`.
- `artifact` — только при вычисленном хеше.
- `labels.hash` — `unavailable | skipped_size`, когда хеша нет; `labels.process` — `unknown`, когда процесс не определён.

### 7.2 Канал `usb`

`action`: `mount | unmount`.

```json
"subject": {
  "drive_letter": "E:",
  "size_bytes": 32015679488,
  "volume": { "type": "removable", "serial": "0781-5583", "label": "KINGSTON", "fs": "FAT32" },
  "device": { "bus": "usb", "vendor": "Kingston", "product": "DataTraveler 3.0", "serial": "0019E06B…" }
}
```

### 7.3 Проверка на сервере

В `services/events._parse_line` после валидации конверта для каналов `file` и `usb` проверяется: действие из словаря канала; обязательные поля `subject` по §7.1 и §7.2 (тип строки, непустота); `volume.type` из перечня. Нарушение — `invalid_event` для этого события (остальные события пакета не страдают). Каналы `agent`, `process` и остальные не проверяются: их схемы вводятся вместе с их сборщиками. Новые действия канала `agent` этого цикла — `watch_overflow` (переполнение буфера уведомлений) и `watch_denied` (нет доступа к наблюдаемому корню); оба с `subject.component = "filewatch"` и путём в `subject.detail`.

## 8. Проверка

| Уровень | Что проверяется |
|---|---|
| Юнит-тесты (любая ОС) | `volumes.Watch`: первый снимок даёт `Mounted`, смена носителя в той же букве, исчезновение; классификация внешнего тома по шине; `debounce`: склейка уведомлений, предел ожидания, создание плюс удаление без события, переименование; `hashindex`: попадание, срок, вытеснение, предел размера; сопоставление `copy`; раскрытие `%USERS%` и фильтр профилей; `exclude`; разбор и границы конфигурации; ограничитель частоты; фабрика и перезапуск группы при смене версии |
| Интеграционные тесты Windows (`//go:build windows`) | настоящий `ReadDirectoryChangesW` на временной папке: создание, запись, переименование, удаление, переполнение; хеш файла; владелец файла; Restart Manager на файле, удерживаемом тестом; снимок томов содержит системный диск |
| Серверные тесты | схема `collectors` (границы, `extra=forbid`); проверка `subject` для `file` и `usb` (допустимое, недостающее поле, чужое действие); события других каналов проходят без проверки |
| Ручная проверка | инструкция `docs/COLLECTORS_MANUAL.md`: вставить флешку, скопировать файл, проверить события в `GET /api/v1/events`; отдельный пункт — удалить и снова вставить флешку; отдельный — копирование большого файла |
| Стенд | `smoke.cmd` без изменений: Docker-агенты на Linux остаются работоспособными |

## 9. Риски и решения

| Риск | Решение |
|---|---|
| Процесс не определяется (быстрое копирование, дескриптор закрыт) | событие уходит без `process` и с `labels.process = "unknown"`; шов под ETW для 2b-2 |
| Хеширование нагружает диск при массовых изменениях | предел размера, ограничитель частоты, склейка по пути, чтение потоком |
| Переполнение буфера уведомлений | событие `agent/watch_overflow`, без тихой потери |
| Файл удерживается другим процессом | повторы до `max_wait_ms`, затем событие без хеша |
| Агент запущен без прав администратора | наблюдаются только доступные папки; ошибки открытия корня журналируются и порождают событие `agent/watch_denied` с путём |
| Опрос томов упускает кратковременное подключение (< 2 с) | принято для аудита; интервал настраивается |
