# BarysGuard DLP — целевая архитектура и дизайн подпроекта 1 (транспорт и PKI)

- **Дата:** 2026-09-08
- **Статус:** на согласовании
- **Автор:** BarysGuard team
- **Область:** общая целевая архитектура системы (разделы 1–5) + детальный дизайн подпроекта 1 (разделы 6–10)

---

## 1. Контекст и цель

BarysGuard существует как настольное приложение под Windows для threat intelligence и реагирования на инциденты. Задача — превратить его в **DLP-комплекс с подсистемой обнаружения по индикаторам компрометации**: сервер на Linux, агенты на конечных хостах, централизованное управление политиками и инцидентами.

Цель проекта — **коммерческий продукт**, а не демонстрационный стенд. Из этого следуют требования, которые для учебной работы были бы избыточны: чистота лицензий зависимостей, версионирование протокола, миграции БД, аудит действий операторов, шифрование хранилища.

Жёсткого срока нет. Приоритет — правильность архитектурных решений над скоростью получения первого работающего результата.

## 2. Исходное состояние

| Компонент | Что есть сейчас |
|---|---|
| «Сервер» | Отсутствует. Его роль выполняет настольное приложение `main.py` на PyQt6 под Windows |
| Агент | `agent/agent.py` — Flask на порту 5555, **pull-модель**: консоль сама опрашивает агента. Аутентификация статическим токеном в `token.txt`, самоподписанный сертификат, клиент не проверяет его (`verify=False`) |
| Хранилище | Файлы `hosts.json` и `config.json` рядом с приложением |
| Детектирование | YARA по запросу, VirusTotal, AbuseIPDB, поиск по хешам и мьютексам |
| Каналы перехвата DLP | Отсутствуют полностью |
| Интерфейс | 11 вкладок PyQt, локализация RU/EN/KZ |

Ценность для переиспользования представляют: `constants.py` (40+ YARA-правил), `core/yara_engine.py`, `core/hash_utils.py` и логика модулей `workers/`.

### 2.1 Лицензионное ограничение

PyQt6 распространяется по двойной лицензии: **GPL v3 либо коммерческая лицензия Riverbank**. Распространение закрытого продукта на GPL-версии обязывает открыть исходный код всего приложения. Это делает развитие настольной консоли несовместимым с коммерческой целью проекта.

**Решение:** настольное приложение замораживается, управление переносится в веб-консоль, где вопрос не возникает.

Остальной планируемый стек лицензионно чист: YARA — BSD-3, yara-python — Apache 2.0, FastAPI, SQLAlchemy, Alembic, Pydantic — MIT/BSD, PostgreSQL — PostgreSQL License, Go и его стандартная библиотека — BSD-3.

## 3. Принятые решения

| Решение | Выбор | Обоснование |
|---|---|---|
| Язык сервера | Python 3.12 | Экосистема разбора документов (docx, xlsx, pdf, архивы) и биндингов YARA существенно богаче альтернатив; разбор содержимого — ядро DLP |
| Веб-фреймворк | FastAPI | Генерация OpenAPI из кода, на которой строится контракт с агентом; асинхронный ввод-вывод |
| СУБД | PostgreSQL 16 | Партиционирование, JSONB, полнотекстовый поиск, `SKIP LOCKED` для очереди — всё в одном продукте |
| ORM и миграции | SQLAlchemy 2.0 + Alembic | Схема будет меняться десятки раз |
| Язык агента | Go 1.23 | Один статический бинарь ~10 МБ без рантайма; кросс-компиляция под Windows и Linux одной командой; служба и демон из общего кода; устойчив к тривиальному вскрытию |
| Транспорт | HTTPS + mTLS, JSON поверх REST | Агент инициирует соединения только наружу; на конечных хостах не открывается ни одного порта |
| Очередь | Таблица в PostgreSQL, `FOR UPDATE SKIP LOCKED` + `LISTEN/NOTIFY` | Транзакционная атомарность с записью события; ноль дополнительной инфраструктуры |
| Полнотекстовый поиск | PostgreSQL FTS за интерфейсом | OpenSearch добавляется при реальной потребности |
| Хранилище артефактов | Файловая система за интерфейсом `ArtifactStore` | Шардирование по префиксу хеша; S3/MinIO подключается подменой реализации |
| Обратный прокси | nginx | Терминация TLS с проверкой клиентских сертификатов, ограничение частоты запросов, отдача веб-консоли |

### 3.1 Осознанные отклонения от исходного плана

Исходный архитектурный план предполагал gRPC, NATS/RabbitMQ, OpenSearch и Redis. От всех четырёх на старте отказываемся.

- **gRPC → HTTPS+mTLS.** Требование «аутентификация агентов по клиентским сертификатам» выполняется полностью. gRPC добавляет генерацию кода, отладку стримов и проблемы прохождения через корпоративные прокси, не давая взамен ничего существенного при выбранной модели опроса команд.
- **NATS → очередь в PostgreSQL.** С внешним брокером невозможна атомарность «событие записано в БД **и** поставлено в очередь»: возникают состояния, где есть одно без другого. Очередь в той же транзакции эту проблему устраняет полностью.
- **OpenSearch → PostgreSQL FTS.** Экономия ~2 ГБ оперативной памяти и одного узла эксплуатации до момента, когда объём данных действительно потребует специализированного поиска.
- **Redis/Bloom → множества в памяти воркера.** Базы индикаторов на десятки миллионов хешей помещаются в память процесса. Redis нужен при горизонтальном масштабировании воркеров на несколько машин.

Все четыре пункта спроектированы как **швы**: интерфейсы `Queue`, `SearchIndex`, `IndicatorSet`, `ArtifactStore` позволяют подменить реализацию без изменения вызывающего кода.

## 5. Границы: что не делаем и почему

Явный список исключений, чтобы к ним не возвращаться в каждом обсуждении.

| Исключено | Причина | Условия пересмотра |
|---|---|---|
| Windows minifilter-драйвер | Kernel-mode, требует подписи драйвера (EV-сертификат, WHQL). Usermode `ReadDirectoryChangesW` покрывает основные сценарии | Отдельная фаза после подпроекта 3; изолированный C-компонент, общается с Go-агентом через порт связи фильтра |
| Перехват содержимого HTTPS (MITM) | Требует внедрения корневого сертификата на хосты и прокси в разрыв. Без него доступны метаданные соединений: IP, FQDN, процесс, объём | Отдельная фаза; технически совместимо с текущей архитектурой |
| Агент под macOS | Endpoint Security Framework требует entitlement от Apple с обоснованием | При наличии спроса |
| STIX/TAXII | Начинаем с фидов IoC в JSON и CSV | Подпроект 3, после стабилизации модели индикаторов |
| Защита процесса агента через PPL/ELAM | Требует драйвера, подписанного Microsoft | Вместе с minifilter |
| Автоматическая регистрация по членству в домене AD | Тянет интеграцию с LDAP и Kerberos | Подпроект 4 |

Отсутствие защиты процесса компенсируется тем, что **пропавшие heartbeat'ы сами являются событием безопасности**: агента можно завершить, но нельзя сделать это незаметно.

# Подпроект 1: транспорт и PKI

## 6. Модель угроз

Проектные решения ниже адресуют конкретный набор угроз.

| Угроза | Мера |
|---|---|
| Подключение поддельного агента | Обязательный mTLS; сертификаты выпускаются только внутренним CA по действительному enrollment-токену |
| Кража enrollment-токена | Одноразовость либо ограниченное число использований, TTL 24 часа, хранение хешем, немедленная видимость регистрации в консоли |
| Кража ключа агента с хоста | Ключ генерируется на хосте и не покидает его; хранение под DPAPI (Windows) и `0600` от root (Linux); отзыв сертификата действует немедленно |
| Выдача себя за другой агент | Личность определяется **серийным номером сертификата**, а не полем в теле запроса |
| Подделка заголовков в обход прокси | nginx вырезает приходящие снаружи `X-Client-*`; приложение отклоняет запрос при `ssl_client_verify != SUCCESS` |
| Повтор ранее отправленных событий | Идемпотентность по `(occurred_at, event_id)`; повтор схлопывается |
| Подмена времени на хосте | Хранятся обе отметки — агента и сервера; расхождение фиксируется и само порождает событие |
| Компрометация хранилища артефактов | Шифрование на диске, ключи завёрнуты мастер-ключом вне БД |
| Злоупотребление со стороны оператора | `audit_log` только на добавление, с цепочкой хешей; отсутствие прав `UPDATE`/`DELETE` у приложения |
| Лавина переподключений после сбоя | Экспоненциальный откат с джиттером на агенте, `429 Retry-After` на сервере |

## 7. PKI и регистрация агента

### 7.1 Удостоверяющий центр

Сервер содержит собственный CA, создаваемый при первом запуске.

- Ключ CA: RSA-4096 либо ECDSA P-384, хранится на файловой системе с правами `0600`, зашифрован парольной фразой из переменной окружения `BG_CA_PASSPHRASE`.
- Сертификат CA публикуется через `GET /gateway/v1/ca` (без аутентификации) и вкладывается в дистрибутив агента.
- Срок действия CA — 10 лет. Структура модуля допускает добавление промежуточного УЦ без изменения протокола.

### 7.2 Последовательность регистрации

```
   │◄────────── BG-ENROLL-a3f9… (TTL 24 ч, лимит N) ───────────│
```

### 7.3 Параметры

| Параметр | Значение |
|---|---|
| Тип ключа агента | ECDSA P-256 |
| CN сертификата | `agent_id` (UUIDv4, генерируется сервером) |
| SAN | DNS-имя хоста на момент регистрации, информационно |
| Субъект CSR | Игнорируется сервером |
| Срок сертификата | 90 дней |
| Порог автопродления | 60 дней с момента выпуска (2/3 срока) |
| Проверка отзыва | Поиск серийного номера в `agent_certificates` на каждом запросе, кеш 10 секунд |
| Срок enrollment-токена | 24 часа, настраивается |
| Формат токена | `BG-ENROLL-` + 32 символа base32; в БД хранится SHA-256 |

Отказ от CRL и OCSP сознателен: для замкнутого внутреннего УЦ проверка по таблице даёт **мгновенный** отзыв вместо ожидания срока обновления списка.

Субъект в CSR агента сервером не используется: агент на момент формирования запроса ещё не знает своего `agent_id`. Сервер подписывает **открытый ключ** из CSR, а субъект сертификата формирует самостоятельно, присвоив `agent_id`. Это устраняет циклическую зависимость и соответствует обычной практике удостоверяющих центров.

### 7.4 Хранение ключа на хосте

- **Windows:** `%ProgramData%\BarysGuard\pki\`, ACL только для `SYSTEM` и `Administrators`, содержимое ключа дополнительно защищено DPAPI на машинном ключе.
- **Linux:** `/var/lib/barysguard/pki/`, владелец `root`, права `0600`, каталог `0700`.

## 8. Протокол

Все эндпоинты под префиксом `/gateway/v1/`. Контракт описан OpenAPI-схемой, которая является **единственным источником истины**: сервер валидируется против неё, клиент агента генерируется из неё.

| Метод и путь | mTLS | Назначение |
|---|---|---|
| `GET /ca` | нет | Сертификат CA в PEM |
| `POST /enroll` | нет | Токен + CSR → сертификат, `agent_id`, начальный конфиг |
| `POST /renew` | да | CSR → новый сертификат по действующему |
| `POST /heartbeat` | да | Состояние агента → версия конфига, очередь команд, требуемый интервал опроса |
| `GET /config` | да | Пакет политик, если `config_version` изменилась |
| `POST /events` | да | Пакет событий в NDJSON, идемпотентно |
| `POST /artifacts` | да | Загрузка содержимого чанками с докачкой |
| `POST /commands/{id}/result` | да | Результат выполнения команды |

### 8.1 Модель доставки

Асимметричная, и это принципиально:

- **События агент → сервер отправляются немедленно** при возникновении. Задержка обнаружения утечки — секунды.
- **Команды сервер → агент** забираются на heartbeat. Интервал по умолчанию 30 секунд, управляется сервером в ответе; при активном инциденте сервер снижает его до 5 секунд.

Постоянные соединения (gRPC-стримы, WebSocket) дали бы мгновенную доставку команд ценой проблем с корпоративными прокси, усложнения балансировки и собственной логики переподключения. В DLP критична задержка **обнаружения**, а не доставки команды. Модель опроса заменяется на long-polling без изменения форматов данных, если потребуется.

### 8.2 Ограничение частоты и обратное давление

- nginx ограничивает частоту запросов по IP и по серийному номеру сертификата.
- При перегрузке сервер отвечает `429` с заголовком `Retry-After`.
- Агент применяет экспоненциальный откат с полным джиттером: базовая задержка 1 с, потолок 300 с.

Джиттер обязателен: без него 5000 агентов после перезапуска сервера создают синхронную волну, укладывающую его повторно.

```json
    "path":    "C:\\Windows\\explorer.exe",
    "cmdline": "explorer.exe",
    "sha256":  "9f2e4c…",
    "signer":  "Microsoft Windows"
  },
  "subject": {
    "src_path": "C:\\Users\\ivanov\\Documents\\отчёт.xlsx",
    "dst_path": "E:\\отчёт.xlsx",
    "volume":   { "type": "removable", "serial": "0781-5583", "label": "KINGSTON" }
  },
  "artifact": { "sha256": "a3f91b…", "size": 184320, "uploaded": false },
  "labels":   {}
}
```

- `event_id` — UUIDv7, генерируется агентом. Монотонность по времени даёт локальность при вставке в индекс.
- `channel` — `file` | `usb` | `clipboard` | `network` | `print` | `process` | `agent`.
- `subject` — единственная часть, специфичная для канала; валидируется отдельной схемой по значению `channel`.
- `schema_version` — позволяет агенту версии 1.0 продолжать работу после перехода сервера на схему 3. Одномоментного обновления флота из тысяч хостов не бывает.
- `severity_hint` — предварительная оценка агента; окончательная критичность определяется сервером.

### 9.1 Учёт времени

Хранятся три величины:

- `occurred_at` — по часам агента;
- `received_at` — по часам сервера;
- `clock_skew_ms` — дрейф часов агента, вычисляемый по heartbeat'ам.

Часы на хосте могут быть неверными или подкрученными намеренно. Для доказательной базы значимы обе отметки, а само расхождение сверх порога порождает событие канала `agent`.

## 10. Offline-буфер агента

Событие **сначала записывается в локальное хранилище и только затем отправляется**. Обратный порядок теряет события при обрыве связи.

| Параметр | Значение по умолчанию |
|---|---|
| Хранилище | bbolt, файл в рабочем каталоге агента |
| Шифрование | AES-256-GCM; ключ под DPAPI (Windows) либо в файле `0600` (Linux) |
| Предел по объёму | 500 МБ |
| Предел по возрасту | 7 суток |
| Политика вытеснения | Первыми удаляются самые старые события низкой критичности. События `critical` не удаляются никогда |
| Порядок отправки | FIFO, пакетами до 500 событий или 4 МБ |
| Подтверждение | Запись удаляется из буфера только после `2xx` от сервера |

Шифрование буфера обязательно: в нём находятся фрагменты перехваченных документов.

## 11. Схема базы данных

Подпроект 1 реализует блоки 1–4 и 6. Блок 5 проектируется здесь для связности миграций, реализуется в подпроекте 3.

### Блок 1 — флот и удостоверения

```
agent_groups
  id · name · parent_id · created_at
  дерево групп; к узлам привязываются политики и область видимости ролей

agents
  id (uuid) · machine_id · hostname · os · os_version · arch
  agent_version · group_id · status · enrolled_at · last_heartbeat_at
  clock_skew_ms · config_version · last_ip · tags (jsonb)
  status: pending | active | offline | quarantined | revoked

enrollment_tokens
  id · token_sha256 · created_by · group_id · expires_at
  max_uses · used_count · revoked_at

agent_certificates
  id · agent_id · serial (уникален) · fingerprint_sha256
  not_before · not_after · revoked_at · revocation_reason · superseded_by
```

Сертификаты вынесены в отдельную таблицу, а не в поле `agents`: за время жизни агента их накапливается десяток, и при расследовании требуется знать, каким именно сертификатом подписано событие полугодовой давности.

### Блок 2 — события

```
events   ПАРТИЦИОНИРОВАНА ПО МЕСЯЦАМ (RANGE по occurred_at)
  PK = (occurred_at, event_id)
  agent_id · schema_version · channel · action · occurred_at · received_at
  actor (jsonb) · process (jsonb) · subject (jsonb)
  artifact_sha256 · artifact_id · labels (jsonb) · severity · verdict_id
```

В партиционированной таблице PostgreSQL первичный ключ обязан включать ключ партиционирования, поэтому уникальность по одному `event_id` невозможна. Идемпотентность строится на паре `(occurred_at, event_id)`; агент присылает обе величины, повторная отправка схлопывается через `ON CONFLICT DO NOTHING`.

Менеджер партиций создаёт разделы на месяц вперёд по расписанию и отцепляет просроченные операцией `DETACH` — мгновенной, в отличие от `DELETE` на сотнях миллионов строк. Гранулярность допускает изменение для будущих периодов без перестройки существующих: разделы RANGE обязаны лишь не пересекаться.

### Блок 3 — артефакты

```
artifacts
  id · sha256 (уникален) · size · mime · storage_path
  first_seen_at · ref_count · encrypted · scan_status

upload_sessions
  id · artifact_sha256 · expected_size · received_bytes · expires_at
```

Адресация по содержимому даёт дедупликацию. Один документ, скопированный пятьюдесятью сотрудниками, — это пятьдесят событий, **один** артефакт на диске и **один** запуск YARA. На реальном контуре разница на порядок и по объёму хранения, и по нагрузке.

### Блок 4 — управление

```
commands
  id · agent_id · type · payload (jsonb) · status
  created_by · created_at · sent_at · completed_at · result (jsonb) · expires_at
  status: queued | sent | running | done | failed | expired

event_queue
  id · event_occurred_at · event_id · enqueued_at · attempts · locked_until
  ссылка на событие составная — первичный ключ events partitioned
  обрабатывается через SELECT … FOR UPDATE SKIP LOCKED
```

Срок годности команды обязателен. Команда «изолировать хост», доставленная через три недели после закрытия инцидента, — это авария, а не запоздалая реакция.

### Блок 5 — детектирование (подпроект 3)

```
policies · rules · rule_versions
  типы правил: regex | dictionary | yara | hash | network | behavior
dictionaries · dictionary_terms
ioc_feeds · ioc_indicators
  тип · значение · нормализованное значение · источник · достоверность · срок
verdicts        какие правила сработали и с каким весом
incidents       severity · score · status · ответственный
incident_events связь многие-ко-многим
```

`rule_versions` существует ради одного: вердикт ссылается на **конкретную версию** правила. Через год при разборе инцидента необходимо понимать, по какой формулировке он сработал, а не по той, до которой правило успели отредактировать.

### Блок 6 — операторы и аудит

```
users · roles · permissions
  роль включает область видимости: поддерево agent_groups
  подпроект 1 реализует роли admin и operator

audit_log
  id · at · user_id · action · target_type · target_id · payload (jsonb)
  prev_hash · hash
  только добавление; приложению не выдаются права UPDATE и DELETE
```

Цепочка хешей делает незаметную правку истории невозможной. DLP-система наблюдает за сотрудниками, и первый вопрос любой проверки — кто контролирует тех, кто читает перехват.

## 12. Конвейер обработки

```
агент ──POST /events──► Gateway ──► 202 Accepted
                           │
                           │ в одной транзакции:
                           │   INSERT events
                           │   INSERT event_queue
                           │   NOTIFY
                           ▼
                    очередь в PostgreSQL
                           │  SELECT … FOR UPDATE SKIP LOCKED
                           ▼
                        Worker
     1. нормализация и обогащение
        путь → тип носителя · домен → организация · процесс → подпись
     2. дешёвые проверки
        хеш по множеству в памяти · расширение · MIME · размер · IP · FQDN
     3. средние
        извлечение текста: docx, xlsx, pdf, архивы
        regex и словари: ИИН, БИН, номера карт, ключи API, приватные ключи
     4. дорогие
        YARA по содержимому · цифровые отпечатки документов
     5. Incident Score → вердикт → создание либо дополнение инцидента
```

Обработчик запроса выполняет только валидацию и запись — агент получает ответ за миллисекунды. Вся тяжёлая работа выполняется отдельными процессами воркеров, масштабируемыми числом копий.

Порядок стадий от дешёвых к дорогим определяет стоимость эксплуатации: проверка хеша по множеству в памяти занимает микросекунды, YARA по 40-мегабайтному PDF — секунды. При потоке в тысячу событий в секунду это разница между одним сервером и двадцатью.

Стадии 2–4 реализуются в подпроекте 3. В подпроекте 1 воркер выполняет стадии 1 и 5 в вырожденном виде: нормализация и запись без детектирования.

## 13. Шифрование хранилища артефактов

Хранилище артефактов представляет собой собрание всех конфиденциальных документов организации, которые кто-либо пытался передать наружу. По ценности для атакующего это самая привлекательная цель во всей сети.

- Каждый артефакт шифруется собственным ключом, AES-256-GCM.
- Ключи артефактов завёрнуты мастер-ключом.
- Мастер-ключ поступает из переменной окружения либо файла секретов, **не из базы данных**.
- Компрометация дампа БД не даёт доступа к содержимому файлов.

Плохо спроектированная DLP-система создаёт больший риск утечки, чем предотвращает.

## 14. Хранение и удаление данных

Сроки настраиваются по каналу и критичности. Значения по умолчанию:

| Данные | Срок |
|---|---|
| События | 1 год |
| Артефакты | 90 дней |
| Инциденты | бессрочно |
| `audit_log` | бессрочно |

Поддерживается повторная проверка сохранённых артефактов обновлёнными правилами. Вердикты являются производной величиной и пересчитываются; исходные данные не удаляются раньше установленного срока.

## 17. Наблюдаемость

- Структурированные журналы в JSON.
- Метрики Prometheus: события в секунду, глубина очереди и лаг обработки, длительность стадий конвейера, число живых агентов, глубина offline-буферов, ошибки TLS-хендшейка.
- Эндпоинты `/health` (процесс жив) и `/ready` (БД доступна, миграции применены).

## 18. Совместимость версий

Правило: **агент версии N работает с сервером версий N и N+1.** Схема события версионирована, сервер принимает предыдущие версии. Требование «обновите весь флот, затем сервер» невыполнимо на реальном внедрении.

## 19. Тестирование

Разработка ведётся по TDD: тест предшествует коду. Для системы, где агент установлен на чужих машинах и обновляется тяжело, цена регрессии несопоставима с ценой теста.

### Уровни

1. **Модульные.** `pytest` и `go test`. Разбор конверта события, вычисление скора, нормализация индикаторов, политика вытеснения буфера.
2. **Интеграционные — на настоящем PostgreSQL** через `testcontainers`. Партиционирование, `SKIP LOCKED` и `ON CONFLICT` на SQLite ведут себя иначе и дают ложную уверенность.
3. **Контрактные.** Сервер валидируется против `api/gateway-v1.yaml`, клиент агента генерируется из неё. Расхождение выявляется в CI.
4. **Сквозные.** Реальный бинарь агента в контейнере против реального сервера.

### Обязательные тесты безопасности

| Сценарий | Ожидаемый результат |
|---|---|
| Подделка заголовков `X-Client-*` в обход nginx | `403` |
| Повторное использование израсходованного enrollment-токена | `403` |
| Просроченный enrollment-токен | `403` |
| Сертификат, подписанный сторонним CA | Отказ на TLS-хендшейке |
| Отозванный сертификат | `403` немедленно, без ожидания истечения кеша |
| Просроченный сертификат агента | Отказ |
| Событие с чужим `agent_id` при валидном сертификате | `403` |
| Обрыв связи на 24 часа | Ноль потерь, ноль дублей |
| Переполнение offline-буфера | Вытеснены старые низкоприоритетные, `critical` сохранены |
| 5000 агентов, одновременно переподключающихся | Сервер обслуживает, откат с джиттером разводит волну |

## 20. CI

| Проверка | Инструмент | Условие отказа |
|---|---|---|
| Python: линт, типы, тесты | `ruff`, `mypy --strict`, `pytest` | Любая ошибка |
| Go: анализ, тесты, сборка | `go vet`, `go test`, матрица `GOOS=windows,linux` | Любая ошибка |
| Миграции | `alembic upgrade head` и `downgrade base` | Ошибка применения либо отката |
| Лицензии зависимостей | `pip-licenses`, `go-licenses` | **Обнаружена GPL или AGPL** |
| Уязвимости | `pip-audit`, `govulncheck` | Уязвимость с оценкой high и выше |
| Образы | `docker build` | Ошибка сборки |

Проверка лицензий не является формальностью: одна GPL-зависимость, затянутая транзитивно, лишает возможности распространять продукт закрытым.

## 21. Развёртывание

**Сервер** — оба пути поддерживаются:

- `docker compose up`: postgres, server, worker, nginx.
- systemd-юниты с внешним PostgreSQL — для сред, где Docker в продуктиве запрещён. Среди заказчиков DLP таких большинство.

**Агент:**

- Windows: MSI на WiX, служба от `SYSTEM`, адрес сервера и enrollment-токен параметрами командной строки для тихой установки через GPO или SCCM.
- Linux: `.deb` и `.rpm` с systemd-юнитом, `Restart=always`.

## 22. Критерии готовности подпроекта 1

Подпроект считается завершённым при одновременном выполнении:

1. Сервер разворачивается на чистой Ubuntu 24.04 по инструкции из репозитория.
2. CA создаётся при первом запуске; сертификат доступен по `GET /gateway/v1/ca`.
3. Оператор создаёт enrollment-токен через REST API.
4. Агент на Windows и агент на Linux регистрируются по токену и получают сертификаты.
5. Агенты отправляют heartbeat; в БД отражаются статус, версия и дрейф часов.
6. Агент отправляет синтетические события; они сохраняются в партиционированную таблицу и проходят через воркер.
7. Останов сервера на 24 часа не приводит к потере или дублированию событий.
8. Отзыв сертификата немедленно прекращает обслуживание агента.
9. Все тесты из раздела 19 проходят.
10. Нагрузочный тест на 5000 симулированных агентов выполняется без деградации.
11. CI зелёный, включая проверку лицензий.
12. Ключи VirusTotal и AbuseIPDB отозваны и перевыпущены, история репозитория очищена.
