# BarysGuard DLP — воркер инспекции содержимого (подпроект 3b / B2)

- **Дата:** 2026-10-06
- **Статус:** проект, ожидает просмотра
- **Область:** серверная инспекция содержимого файлов, загруженных с внешних томов: очередь, воркер, извлечение текста, правила (ИИН/БИН, банковские карты, словарь грифов), вердикты, инциденты и API чтения. Индикаторы компрометации и YARA — B3; страница инцидентов и редактор правил — подпроект C.
- **Опора:** разделы 11 («Блок 3 — артефакты», «Блок 4 — управление», «Блок 5 — детектирование»), 12, 13 основной спеки `2026-09-08-dlp-transport-core-design.md`; загрузка артефактов `2026-10-05-artifact-upload-design.md`; конвейер событий `2026-10-05-event-pipeline-design.md`.

**Критерий завершения:** файл с валидным ИИН и номером банковской карты, скопированный на флешку (или загруженный сидом на стенде), даёт вердикт `flagged` и инцидент в `GET /api/v1/incidents`; файл без чувствительных данных даёт вердикт `clean` и не даёт инцидента; повторное копирование того же файла не запускает повторный скан; содержимое файлов и полные значения совпадений нигде не сохраняются в открытом виде; `.\test.cmd` зелёный.

## 1. Границы

### 1.1 Что входит

| Часть | Содержание |
|---|---|
| База данных | одна миграция: `event_queue`, `rules`, `rule_versions`, `dictionaries`, `dictionary_terms`, `artifact_scans`, `verdicts`, `incidents`, `incident_events`; колонка `events.verdict_id` |
| Сервер | пакет `barysguard/services/inspection/` (извлечение текста, детекторы, оценка, постановка в очередь, воркер, инциденты); команды `barysguard-admin worker` и `seed-rules` |
| API | `GET /api/v1/incidents`, `GET /api/v1/incidents/{id}`, `PATCH /api/v1/incidents/{id}`; поле `verdict` в `GET /api/v1/events` |
| Стенд | сервис `worker` в `docker-compose` стенда |
| Проверка | серверные тесты, сквозная проверка на стенде, документация |

### 1.2 Что не входит

| Не делаем | Почему | Когда |
|---|---|---|
| Архивы (zip, rar, 7z), OCR, YARA, хеши IoC | Каждое — отдельная поверхность атаки и нагрузка | B3 |
| Редактор правил, пользовательские regex | Нужна защита от ReDoS и интерфейс | C |
| Страница инцидентов в консоли, назначение ответственного | Интерфейс | C |
| Скачивание содержимого оператором | Роли и аудит выдачи чужих документов | C |
| Удаление артефактов по сроку хранения | Срок связан с жизненным циклом инцидента | отдельно |
| Пересчёт вердиктов старых событий при смене правил | Не нужен для минимума | отдельно |
| Уведомления, интеграции | Не нужны для минимума | C |
| Секреты разработки (PEM, API-ключи), IBAN, телефоны | Решение: стартовый набор — ИИН/БИН, карты, грифы | по запросу |
| Redis, NATS, OpenSearch | Решение основной спеки: очередь в PostgreSQL | — |

## 2. Принятые решения

| Решение | Выбор | Обоснование |
|---|---|---|
| Когда событие берётся в обработку | Постановка в очередь при завершении загрузки артефакта и при приёме события, если артефакт уже есть; страховочная проверка воркера | Содержимое приходит позже события; воркер не опрашивает «готово ли»; файл, который никогда не загрузится, не висит в очереди |
| Процесс | Отдельный `barysguard-admin worker`, тот же образ | Основная спека, раздел 12: тяжёлая работа вне обработчика запроса |
| Очередь | Таблица `event_queue`, `SELECT … FOR UPDATE SKIP LOCKED` | Основная спека, раздел 3 |
| Единица скана | Хеш артефакта: один скан на `(sha256, версия набора правил)` | Основная спека, блок 3: один документ — один скан |
| Единица вердикта | Событие | Вердикт нужен там, где его читает оператор: у события |
| Извлечение текста | Стандартная библиотека для текста, `docx`, `xlsx`, `pptx`; `pypdf` для PDF | Минимум новых зависимостей |
| Хранение найденного | Счётчики и маскированные образцы, не полные значения | Таблица совпадений не должна стать второй утечкой |
| Правила | Встроенные детекторы с проверкой контрольных сумм; словарь в БД | Нет случайных срабатываний на цифры |
| Группировка инцидентов | Агент + пользователь + хеш артефакта, пока инцидент открыт | 50 копий одного документа с одной машины — один инцидент |

## 3. Данные

Одна миграция. Таблица `events` и её партиции не перестраиваются: добавляются колонка `verdict_id` и частичный индекс `ix_events_artifact_sha256` (по `artifact_sha256`, где он не пуст) — им пользуется постановка в очередь по хешу артефакта.

### 3.1 Таблицы

```
event_queue
  id (bigserial, PK) · event_occurred_at · event_id · artifact_sha256
  enqueued_at · attempts (0) · locked_until · state: pending | failed
  UNIQUE (event_occurred_at, event_id)
  индекс (state, locked_until, id) для выборки пачки

rules
  id · key (уникален: iin_bin | card | markings) · kind: detector | dictionary
  title · enabled · created_at
rule_versions
  id · rule_id · version · params (jsonb: weight, cap, detector, dictionary_id)
  created_at · UNIQUE (rule_id, version)

dictionaries · id · key (уникален) · title
dictionary_terms · id · dictionary_id · term · UNIQUE (dictionary_id, term)

artifact_scans
  id · artifact_sha256 · ruleset_hash · status
  status: ok | unsupported | no_text | encrypted | too_large | error
  truncated (bool) · findings (jsonb) · scanned_at
  UNIQUE (artifact_sha256, ruleset_hash)

verdicts
  id · event_occurred_at · event_id · scan_id
  status: clean | flagged | not_inspected · reason (для not_inspected)
  score · severity · matches (jsonb) · created_at
  UNIQUE (event_occurred_at, event_id)

incidents
  id · group_key (agent_id|actor|sha256) · agent_id · artifact_sha256
  title · severity · score · status: open | acknowledged | closed
  assignee (null в B2) · first_event_at · last_event_at · events_count
  created_at · closed_at
  частичный UNIQUE (group_key) WHERE status <> 'closed'

incident_events · incident_id · event_occurred_at · event_id · PK по всем трём
```

`events.verdict_id` — nullable идентификатор `verdicts.id`. Внешний ключ не создаётся: ссылки на партиционированную таблицу и с неё в PostgreSQL ограничены, поэтому целостность обеспечивает код, как и для `event_queue`.

`artifacts.scan_status` из миграции B1 остаётся и обновляется воркером: `pending` → `scanned` (или `failed`) — признак для обзора, не источник истины.

### 3.2 Содержимое `findings` и `matches`

`findings` (в скане, общий для всех событий с этим хешем):

```json
{
  "iin_bin": {"rule_version_id": "…", "count": 3, "samples": ["**********12", "**********47"]},
  "card":    {"rule_version_id": "…", "count": 1, "samples": ["************4242"]},
  "markings": {"rule_version_id": "…", "count": 2, "samples": ["конфиденциально"]}
}
```

`matches` (в вердикте) — те же правила со вкладом в оценку: `{rule_key, rule_version_id, count, points}`.

Правила маскирования образцов: ИИН/БИН — остаются 2 последние цифры, карта — 4 последние, термины словаря хранятся как есть (это не пользовательские данные, а слова из словаря). Образцов не больше 5 на правило. Позиции совпадений не записываются.

### 3.3 Версии правил и набора

Изменение правила или словаря создаёт новую `rule_version` (старая остаётся). Для словаря версия правила хранит `dictionary_id` и `terms_hash` на момент создания версии. `ruleset_hash` — SHA-256 от отсортированных `rule_version_id` и `terms_hash` включённых правил. Вердикт ссылается на скан, а скан — на `ruleset_hash`, поэтому через год можно восстановить, по какой формулировке правила сработал вердикт.

Заведение: идемпотентная команда `barysguard-admin seed-rules` (вызывается и из `bootstrap-dev`): создаёт три правила, словарь «Грифы» с терминами и версии 1; повторный запуск не создаёт дубликатов, а при изменении встроенных параметров создаёт новую версию.

## 4. Постановка в очередь

### 4.1 Три точки

1. **Завершение загрузки.** В `services/artifacts._finalize`, в той же транзакции, после записи артефакта: все события с этим `artifact_sha256`, у которых нет записи в `event_queue` и нет `verdict_id`, ставятся в очередь одним `INSERT … SELECT … ON CONFLICT DO NOTHING`.
2. **Приём события.** В `services/events.store_events` после вставки: для вставленных событий с `artifact_sha256`, который уже есть в `artifacts`, — одним запросом постановка в очередь.
3. **Страховка.** Воркер раз в 60 секунд берёт артефакты, появившиеся за последние 24 часа (`first_seen_at`), находит события с их `artifact_sha256` без записи в очереди и без вердикта и ставит их в очередь. Гонка возможна только вокруг завершения загрузки, поэтому обход по свежим артефактам её закрывает и не читает всю таблицу событий. Закрывает гонку, когда транзакции события и завершения загрузки не видят друг друга.

Постановка идемпотентна. События без `artifact_sha256` в очередь не попадают; для них вердикта нет.

### 4.2 Захват и повторы

Воркер забирает пачку (по умолчанию 10) запросом `FOR UPDATE SKIP LOCKED` по задачам `state = pending` и `locked_until` в прошлом или пустым, выставляет `locked_until = now() + BG_WORKER_LOCK_SECONDS` (по умолчанию 300) и увеличивает `attempts`. Успешно обработанная задача удаляется из очереди. Реальная ошибка (БД, расшифровка) оставляет задачу с истечением `locked_until`; после `attempts >= 3` задача получает `state = failed`, а в вердикте пишется `not_inspected` с `reason = "error"`. Статусы скана `unsupported`, `no_text`, `encrypted`, `too_large` — нормальный исход, задача удаляется.

Два воркера не берут одну задачу. Падение воркера посреди обработки освобождает задачу по истечении `locked_until`.

## 5. Воркер

Команда `barysguard-admin worker`. Настройки читает `Settings` (раздел 9). Нужен тот же `BG_ARTIFACT_MASTER_KEY`, что у сервера; без него воркер завершается с понятной ошибкой.

Цикл:

1. Раз в 60 секунд — страховочная постановка (п. 4.1.3).
2. Захват пачки задач.
3. Для каждой задачи: если для хеша и текущего `ruleset_hash` есть скан — взять его; иначе расшифровать артефакт потоком из `ArtifactStore.open`, извлечь текст, применить правила, записать `artifact_scans`.
4. Записать вердикт события, проставить `events.verdict_id`, создать или дополнить инцидент (раздел 8) — в одной транзакции.
5. Если очередь пуста — подождать `BG_WORKER_POLL_SECONDS` (по умолчанию 2).

Остановка — по сигналу: текущая задача дорабатывается, новых не берётся.

## 6. Извлечение текста

Модуль `services/inspection/extract.py`. Формат определяется по сигнатуре и расширению из `subject.dst_path`, а не по заявленному агентом типу.

| Формат | Способ |
|---|---|
| `txt`, `csv`, `json`, `log`, `md`, `xml`, `html`, исходники | Текст в UTF-8; при ошибке `cp1251` |
| `docx`, `xlsx`, `pptx` | `zipfile` + разбор XML стандартной библиотекой: текстовые узлы документа, общие строки и ячейки листов, текст слайдов |
| `pdf` | `pypdf`; документ без текстового слоя — статус `no_text` |
| Остальное, включая архивы | Статус `unsupported` |

Защитные пределы (настраиваются, значения по умолчанию в разделе 9):

- не более 20 МиБ извлечённого текста на файл; остальное отбрасывается, `truncated = true`;
- для zip-контейнеров: не более 200 МиБ суммарного распакованного размера, не более 10000 элементов, степень сжатия не выше 100; нарушение — статус `too_large`;
- таймаут 30 секунд на файл; разбор выполняется в отдельном потоке, превышение — статус `error` без остановки воркера;
- документ, защищённый паролем, — статус `encrypted`;
- имя файла внутри контейнера никогда не используется как путь на диске.

Расшифрованный файл читается в память целиком (не больше `BG_ARTIFACT_MAX_BYTES`, по умолчанию 50 МиБ) и на диск не пишется; извлечённый текст отдаётся детекторам порциями с перекрытием, достаточным для самого длинного совпадения, и совпадение на границе порции не теряется и не считается дважды. Таймаут кооперативный: извлечение и сканирование проверяют срок между порциями и страницами.

## 7. Детекторы и оценка

Модуль `services/inspection/detectors.py`. Каждое совпадение проверяется контрольной суммой.

- **ИИН.** 12 цифр, не часть более длинной цифровой последовательности. Дата рождения `ГГММДД` — реальная календарная; 7-я цифра 1–6 (век и пол); контрольный разряд по стандарту: сумма цифр с весами 1…11 по модулю 11, при остатке 10 повторный проход с весами 3…11, 1, 2, и остаток 10 означает невалидный номер.
- **БИН.** 12 цифр, не часть более длинной последовательности; цифры 3–4 (после года регистрации) — месяц 01–12; 5-я цифра 4, 5 или 6 (тип организации); контрольный разряд тем же алгоритмом. Значение, прошедшее обе проверки (ИИН и БИН), засчитывается один раз.
- **Банковская карта.** 13–19 цифр, допускаются пробелы и дефисы между группами; проверка Луна; префикс сети: Visa (4), Mastercard (51–55, 2221–2720), МИР (2200–2204), Amex (34, 37).
- **Словарь грифов.** Термины из словаря: без учёта регистра, `ё` приравнивается к `е`, совпадение по границам слов; многословные термины допускают произвольные пробельные символы между словами.

Оценка. У `rule_version.params` есть `weight` и `cap`. Вклад правила — `weight × min(count, cap)`. Итог — сумма вкладов, не более 100. Значения для стартового набора:

| Правило | weight | cap |
|---|---|---|
| ИИН/БИН | 20 | 5 |
| Карта | 25 | 4 |
| Грифы | 15 | 2 |

Вердикт:

| Score | Статус | Severity |
|---|---|---|
| 0–19 | `clean` | `info` |
| 20–49 | `flagged` | `medium` |
| 50–79 | `flagged` | `high` |
| 80–100 | `flagged` | `critical` |

Если скан имеет статус `unsupported`, `no_text`, `encrypted`, `too_large` или `error`, вердикт — `not_inspected` с `reason`, равным статусу, score 0, severity `info`; инцидент не создаётся.

Пороги вердикта фиксированы в коде; порог создания инцидента — `BG_INCIDENT_MIN_SCORE` (по умолчанию 20).

## 8. Инциденты

Инцидент создаётся, когда вердикт `flagged` и `score >= BG_INCIDENT_MIN_SCORE`.

- **Ключ группировки:** `agent_id|actor.user_name (или "unknown")|artifact_sha256`. Пока существует инцидент с этим ключом в статусе `open` или `acknowledged`, новое событие добавляется в `incident_events`, `events_count` и `last_event_at` обновляются, `score` и `severity` берутся по максимуму. Закрытый инцидент новое событие не открывает заново: создаётся новый (частичный уникальный индекс по `group_key` для незакрытых это допускает).
- **Заголовок:** строится автоматически из сработавших правил, например «Копирование на USB: ИИН/БИН ×3, гриф ×1» (действие берётся из события).
- **Параллельные воркеры:** создание инцидента — `INSERT … ON CONFLICT` по частичному индексу, затем обновление; гонка двух воркеров не создаёт дубликата.
- **Область видимости:** оператор видит инциденты агентов из своей области (используется тот же механизм `services/scope`, что у событий).

## 10. API

Все маршруты — под авторизацией консоли и с учётом области видимости.

- `GET /api/v1/incidents` — фильтры `status`, `severity`, `agent_id`; курсорная пагинация, как в событиях; сортировка по `last_event_at` по убыванию.
- `GET /api/v1/incidents/{id}` — инцидент, вердикт (status, score, severity), совпадения по правилам (счётчики и маскированные образцы), список событий (идентификаторы и краткие поля). Чужой по области инцидент — `404`.
- `PATCH /api/v1/incidents/{id}` — тело `{"status": "acknowledged" | "closed"}`; недопустимые переходы (из `closed`) — `409`; запись в `audit_log`.
- `GET /api/v1/events` — в каждый элемент добавляется `verdict: {status, score, severity} | null`.

Контракт `api/gateway-v1.yaml` и типы консоли обновляются; страница инцидентов в консоли — не в B2.

## 11. Стенд и деплой

В `deploy/stand/docker-compose.yml` добавляется сервис `worker`: образ сервера, команда `barysguard-admin worker`, те же переменные окружения (БД и `BG_ARTIFACT_MASTER_KEY`) и том `artifacts` (воркер читает зашифрованные файлы). Том PKI, порты и TLS не нужны. Зависит от завершения `bootstrap`. `smoke` расширяется проверкой, что воркер жив и очередь разбирается. Миграция и `seed-rules` выполняются в `bootstrap`.

## 12. Безопасность

- Содержимое артефакта расшифровывается только в памяти, на диск открытым не пишется; разбор контейнеров не распаковывает файлы на диск.
- Полные значения совпадений не сохраняются ни в `artifact_scans`, ни в `verdicts`, ни в логах; в логи воркера попадают идентификаторы, хеши, статусы и счётчики.
- Защита от «бомб»: пределы раздела 6, таймаут, потоковое чтение.
- Имена внутри контейнеров не используются как пути.
- Права на чтение инцидентов следуют области видимости; `PATCH` попадает в `audit_log`.
- Обновление статуса инцидента не раскрывает содержимое; скачивания содержимого в B2 нет.
- Порядок отказов: сбой воркера никогда не удаляет событие и не меняет принятого агентом; худший исход — событие остаётся без вердикта и подбирается страховкой.

---

## 13. Тестирование

- **Детекторы:** валидные и невалидные ИИН и БИН (дата, 7-я цифра, контрольный разряд, часть более длинного числа), карты (Луна, префиксы, разделители, 13 и 19 цифр), словарь (регистр, `ё/е`, границы слов, многословные термины), маскирование, границы порций.
- **Извлечение:** `txt` (UTF-8, cp1251), `docx`, `xlsx`, `pptx`, `pdf` с текстом и без, пароленый файл, zip-бомба (степень сжатия, число элементов, размер), усечение, таймаут.
- **Очередь:** постановка в обоих порядках (событие раньше артефакта и наоборот), страховка, идемпотентность, два воркера и `SKIP LOCKED`, истечение блокировки, три неудачи до `failed`.
- **Оценка и вердикты:** вклады, потолок, пороги; `not_inspected` для каждого статуса скана; скан переиспользуется для второго события с тем же хешем; смена набора правил даёт новый скан.
- **Инциденты:** создание, дополнение, максимум score, новый инцидент после закрытия, гонка двух воркеров, заголовок, область видимости, `PATCH` и аудит, недопустимый переход.
- **API:** фильтры, пагинация, `404` вне области, поле `verdict` в событиях, соответствие контракту `gateway-v1.yaml`.
- **Сквозной:** на стенде сид кладёт артефакт с валидными ИИН и номером карты через протокол загрузки; проверяется инцидент в `GET /incidents`, отсутствие инцидента для чистого файла и отсутствие повторного скана при втором событии с тем же хешем. Ручная проверка на реальном агенте — по шагам из документации.

## 15. Порядок реализации (набросок для плана)

1. Миграция и модели, `seed-rules`.
2. Детекторы и оценка (чистые функции, без БД).
3. Извлечение текста с защитными пределами.
4. Очередь: постановка (три точки) и захват.

7. API и контракт, поле `verdict` в событиях.
8. Стенд, сквозная проверка, документация.

## 16. Открытые вопросы

- Пересчёт вердиктов старых событий при смене правил — не нужен для B2; решение откладывается до появления редактора правил.
- Срок хранения вердиктов, сканов и инцидентов; удаление артефактов вместе с ними.
- Нужен ли отдельный признак «защищён паролем» в `GET /events` для оператора (сейчас виден только через вердикт).
