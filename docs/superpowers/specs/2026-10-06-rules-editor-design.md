# BarysGuard DLP — редактор правил и словарей в консоли (подпроект C2)

- **Дата:** 2026-10-06
- **Статус:** проект, ожидает просмотра
- **Область:** управление правилами инспекции из консоли: включение и отключение встроенных правил, изменение веса и потолка, словарь грифов и собственные словари, собственные правила по регулярному выражению, проверка шаблона на тестовом тексте, встроенная инструкция. Не входят границы вердикта (20/50/80), удаление правил, пересканирование старых событий, права для не-администраторов.
- **Опора:** `2026-10-06-dlp-worker-design.md` (правила, версии, сканирование, вердикты), `2026-10-04-web-console-cycle-1-design.md` (структура консоли), страница инцидентов (`web/src/features/incidents`).

**Критерий завершения:** администратор в консоли отключает встроенное правило и меняет вес другого; добавляет и удаляет термин в словаре грифов; создаёт собственный словарь и собственное regex-правило с проверкой на тестовом тексте; файл, скопированный на флешку после этого, оценивается по новым правилам и даёт инцидент с названием его правила; все изменения видны в журнале аудита; регулярные выражения не могут зависнуть воркер; полные значения совпадений по собственным правилам нигде не хранятся; `.\test.cmd` зелёный.

## 1. Границы

### 1.1 Что входит

| Часть | Содержание |
|---|---|
| Сервер | `api/rules.py` (список, создание, изменение, термины, история версий, проверка шаблона); `services/inspection/rule_admin.py` (публикация версий, валидация); детектор `RegexDetector` на RE2; изменение `ContentScanner` и словарного детектора (регистр и `ё/е` без глобального приведения текста); `seed-rules` перестаёт перезаписывать правки оператора; название правила в `matches` |
| Консоль | страница «Правила» (список, окно правила, термины, проверка шаблона, вкладка «Как создавать правила»), пункт меню только для администратора, названия своих правил в карточке инцидента |
| Документация | `docs/RULES_GUIDE.md` (та же инструкция), правки `docs/DLP_WORKER.md` |
| Проверка | серверные и консольные тесты, проверка на стенде |

### 1.2 Что не входит

| Не делаем | Почему |
|---|---|
| Границы вердикта 20/50/80 и порог инцидента | зашиты в коде, отдельная настройка при необходимости |
| Удаление правил | вердикт ссылается на версию правила; отключённое правило остаётся для расшифровки старых вердиктов |
| Пересканирование старых событий | отдельная функция (очередь пересчёта) |
| Просмотр и правка правил оператором | решение: правила и словари видит и меняет только администратор |
| Импорт и экспорт правил | не нужны для минимума |
| Тип `detector` для пользователей (ИИН, карта) | встроенные детекторы с контрольными суммами остаются кодом |

## 2. Принятые решения

| Решение | Выбор | Обоснование |
|---|---|---|
| Доступ | только администратор (`require_admin`), для остальных `403`, пункт меню скрыт | набор правил и словарь показывают, что именно ловит система |
| Движок regex | RE2 (`google-re2`), линейное время | стандартный `re` допускает катастрофический поиск, воркер нельзя остановить посреди вызова; для Python 3.13 есть wheel под Windows и Linux |
| Ограничения regex | шаблон до 500 символов, совпадение до 200 символов, пустое совпадение запрещено, без lookaround и обратных ссылок (RE2 их не поддерживает) | предсказуемая стоимость и потоковое сканирование с фиксированным перекрытием |
| Обязательная проверка | сохранить regex можно, только прислав тестовый текст, на котором найдено не меньше одного совпадения | отсекает опечатки; сервер перепроверяет при сохранении |
| Что считается изменением | вес, потолок, шаблон, опция регистра, термины словаря — новая версия правила; название и включение — без новой версии | вердикт ссылается на версию, на которой он получен |
| Применение | только к новым сканам; `ruleset_hash` меняется, старые сканы и вердикты остаются | как в спеке воркера |
| Хранение образцов | для regex — маска (все символы, кроме двух последних, заменяются `*`); полное совпадение не сохраняется | прежнее правило конфиденциальности |
| Название в инциденте | в `matches` добавляется `rule_title`; заголовок инцидента строится по названию, для встроенных — по прежним подписям | свои правила не имеют встроенных подписей |

## 3. Данные

Миграция не добавляет таблиц: используются `rules`, `rule_versions`, `dictionaries`, `dictionary_terms`.

- `rules.kind` получает значение `regex` (сейчас `detector` и `dictionary`). Добавляются колонки `rules.builtin` (bool, по умолчанию `false`; для трёх встроенных `true`) и `rules.updated_at`. Миграция проставляет `builtin = true` для ключей `iin_bin`, `card`, `markings`.
- Ключ своего правила: `custom_<8 шестнадцатеричных знаков>`, уникален.
- Параметры версии (`rule_versions.params`):
  - детектор: `{detector, weight, cap}` (как сейчас);
  - словарь: `{weight, cap, dictionary_id, terms_hash}`; у встроенного словаря `markings` и у собственных словарей одна форма;
  - regex: `{pattern, ignore_case, weight, cap}`.
- Собственный словарь — строка в `dictionaries` (ключ `custom_<…>`), его термины в `dictionary_terms`.
- `weight` — целое 1…100, `cap` — целое 1…50; название — до 120 символов.

`seed_rules` меняется: правило и версия 1 создаются, только если правила ещё нет; существующие правила, их версии и термины не трогаются. (Новые значения по умолчанию в будущих релизах применять отдельной миграцией данных.)

## 4. Сканер и детекторы

### 4.1 Регистр и ё/е

Сейчас `ContentScanner.feed` приводит весь текст к нижнему регистру и заменяет `ё` на `е`. Это ломает собственные шаблоны (прописные буквы в шаблоне перестают совпадать). Изменение:

- `ContentScanner` больше не нормализует текст;
- `DictionaryDetector` строит шаблон с флагом `re.IGNORECASE`, заменяя в каждом термине `е`/`ё` на класс `[еёЕЁ]`; образец совпадения для словаря нормализуется (`normalize`) только при записи;
- встроенные детекторы ИИН/БИН и карт работают с цифрами и от регистра не зависят.

Тесты сканера (в том числе проверка «любой размер порции даёт тот же результат») сохраняются и расширяются.

### 4.2 RegexDetector

`services/inspection/regex_detector.py`: `RegexDetector(key, pattern, ignore_case)` на RE2 (`re2.compile`). Реализует `find(data, start, end)` как остальные детекторы. Особенности:

- `max_length = 200` (настройка `BG_REGEX_MAX_MATCH`): совпадение длиннее 200 символов не засчитывается, поэтому перекрытие `max_length + 2` достаточно для потокового сканирования; совпадение считается одинаково при любом разбиении текста на порции;
- пустое совпадение не засчитывается;
- образец — маска: все символы, кроме двух последних, заменяются `*` (для совпадений короче трёх символов — все `*`);
- у RE2 нет lookbehind, поэтому контекстный символ перед порцией ему не нужен.

### 4.3 Загрузка правил

`Ruleset.detectors()` для `kind == "regex"` создаёт `RegexDetector`; `RuleRuntime` получает `title` и, для regex, `pattern`/`ignore_case`; в `RuleWeight` и `matches` добавляется `rule_title`. Если шаблон версии не компилируется (повреждённые данные), правило пропускается с записью в лог (без шаблона и содержимого) — воркер не падает.

## 5. Сервер: API

Все маршруты под `/api/v1`, доступ только администратору, изменения пишутся в `audit_log`.

| Маршрут | Действие |
|---|---|
| `GET /rules` | список: `id, key, kind, title, builtin, enabled, version, weight, cap, updated_at`, для словарей `terms_count`, для regex `pattern, ignore_case` |
| `POST /rules` | создать своё правило: `{kind: "dictionary" \| "regex", title, weight, cap, pattern?, ignore_case?, test_text?, terms?}`; для regex обязателен `test_text` с хотя бы одним совпадением; ответ — правило |
| `GET /rules/{id}` | правило с параметрами текущей версии |
| `PATCH /rules/{id}` | `{title?, enabled?, weight?, cap?, pattern?, ignore_case?, test_text?}`; изменение параметров версии создаёт новую версию; `pattern` и `ignore_case` только у regex (при смене шаблона обязателен `test_text`) |
| `GET /rules/{id}/versions` | история: версия, параметры, когда создана |
| `GET /rules/{id}/terms` | термины словаря (параметры `q`, `limit`, `offset`) |
| `POST /rules/{id}/terms` | `{terms: [..]}` — добавить пачкой (строки обрезаются, пустые и повторы отбрасываются, до 500 за вызов, термин до 200 символов); создаётся новая версия |
| `DELETE /rules/{id}/terms/{term_id}` | удалить термин; создаётся новая версия |
| `POST /rules/test` | `{kind, pattern?, ignore_case?, terms?, text}` → `{ok, error?, count, matches: [{start, end}]}`; текст до 20 000 символов, не сохраняется и не пишется в лог, в ответе только позиции |

Правила проверки: вес и потолок в пределах раздела 3; название непустое; у regex — шаблон компилируется в RE2, не длиннее 500 символов, не совпадает с пустой строкой; для встроенных правил нельзя менять `kind`, `key`, `pattern`; встроенный `detector`-тип редактируется только по весу, потолку и включению. Ошибки валидации — `422` с понятным текстом (для шаблона — сообщение RE2 без содержимого теста). Нельзя отключить все правила сразу: отключение последнего включённого правила — `409` (воркер без правил не берёт задач, спека воркера, §I3).

Публикация версии (`rule_admin.publish_version`): под блокировкой строки правила; для словарей `terms_hash` пересчитывается по текущим терминам; новая версия создаётся только если параметры реально изменились.

## 6. Консоль

Страница `/rules` (меню «Правила», только администратор; прямой переход оператора ведёт на главную, как у страниц, недоступных по роли).

- **Список.** Таблица: название, тип («Встроенное», «Словарь», «Шаблон»), переключатель «Включено», вес, потолок, версия, «Изменить». Кнопка «Создать правило» (тип «Словарь» или «Шаблон»). Переключатель включения сразу отправляет `PATCH` с уведомлением; ошибка (например, последнее правило) показывается уведомлением, переключатель возвращается.
- **Окно правила.** Название, вес, потолок (поля с пределами), для regex — шаблон, «Без учёта регистра», блок «Проверка» (многострочное поле с тестовым текстом, кнопка «Проверить», результат: число совпадений и подсветка найденных фрагментов, сообщение об ошибке шаблона); «Сохранить» для regex недоступна, пока проверка не нашла совпадение; для словарей — список терминов с поиском, поле «Добавить термины (по одному в строке)», удаление термина; вкладка «История версий» (версия, дата, параметры).
- **Вкладка «Как создавать правила»** на странице списка (статичный текст из `i18n/ru.ts`): что такое правило, вес, потолок и как считается оценка, таблица порогов вердикта (0–19 чисто, 20–49 средняя, 50–79 высокая, 80+ критическая) и порог инцидента, словарные правила (регистр и `ё/е` не важны, границы слов), правила-шаблоны (синтаксис RE2, примеры: номер договора `№\s?\d{4}-\d{3}`, внутренний код проекта `ALFA-\d{3,5}`, чего нельзя: lookahead/lookbehind и обратные ссылки, лимиты 500/200 символов), как проверять шаблон, как применяется изменение (только к новым файлам), как отключить шумное правило.
- **Инциденты.** В таблице совпадений используется `rule_title` для собственных правил.

## 7. Безопасность

- Все маршруты `require_admin`; тесты на `403` для оператора и на отсутствие пункта меню.
- RE2 исключает катастрофический поиск; лимиты длины шаблона и совпадения; тестовый текст ограничен 20 000 символов и обрабатывается в `to_thread` с тем же кооперативным ограничением времени.
- Тестовый текст и шаблоны не попадают в логи и в тексты исключений; в аудит пишутся идентификатор правила, поле и значения параметров, но не тестовый текст; шаблон в аудит попадает (это конфигурация, не данные).
- Образцы собственных правил маскируются; полное совпадение нигде не хранится.
- Изменения конкурентно безопасны: блокировка строки правила при публикации версии.

## 9. Тестирование

- **Сканер:** регистронезависимый словарь, `ё/е`, границы слов, неизменность результата при любом размере порции (в том числе с `RegexDetector`), совпадение длиннее лимита не засчитывается одинаково при любом разбиении.
- **RegexDetector:** простые шаблоны, `ignore_case`, пустое совпадение, маскирование, шаблоны, не поддерживаемые RE2 (lookahead, обратная ссылка) отклоняются при валидации, длинный шаблон отклоняется.
- **Правила:** `seed_rules` не перезаписывает правки и термины; публикация версии (новая версия только при изменении параметров; термины меняют `terms_hash`); `ruleset_hash` меняется после правки; повреждённый шаблон пропускается без падения воркера.
- **API:** `403` для оператора и анонима на каждом маршруте; список, создание словаря и regex (валидация, обязательная проверка), `PATCH` (вес, потолок, включение, шаблон, название), встроенные правила неприкосновенны по `kind/key`; отключение последнего правила — `409`; термины (пачкой, повторы, лимиты, удаление); история версий; `POST /rules/test` (совпадения, ошибка шаблона, лимит текста, текст не попадает в логи); аудит каждой записи; контракт OpenAPI и типы консоли.
- **Сквозной:** создать правило-шаблон через API, отправить файл с совпадением через протокол загрузки, воркер даёт инцидент с названием правила; отключить встроенное правило — следующий файл его не учитывает.
- **Консоль (vitest):** список и переключатель, окно правила (валидации полей, проверка шаблона и блокировка «Сохранить»), термины (добавление пачкой, поиск, удаление), создание словаря и шаблона, вкладка с инструкцией, скрытие пункта меню для оператора, ошибки API.
- **Стенд:** вручную по шагам в документации.

## 10. Порядок реализации (набросок для плана)

1. Зависимость RE2, настройки, миграция (`builtin`, `updated_at`, значения `kind`), изменение `seed_rules`.
2. Сканер: регистр и `ё/е` внутри словарного детектора; `RegexDetector`; загрузка `regex`-правил в `Ruleset`; `rule_title` в совпадениях.
3. Сервис `rule_admin` (валидация, публикация версий, термины).
4. API правил и контракт.
5. Консоль: типы, список, окно правила, термины, проверка шаблона.
6. Инструкция (вкладка и `docs/RULES_GUIDE.md`), правки документации.
7. Сквозной тест, проверка на стенде.
