# BarysGuard DLP — загрузка и хранение артефактов (подпроект 3a / B1)

- **Дата:** 2026-10-05
- **Статус:** реализовано (подпроект 3a / B1)
- **Область:** доставка содержимого файлов с внешних томов от агента к серверу и его шифрованное хранение. Инспекция содержимого (воркер, правила, вердикты, инциденты) — подпроект B2; индикаторы компрометации и YARA — B3; страницы инцидентов и редактор правил — подпроект C.
- **Опора:** разделы 8, 11 («Блок 3 — артефакты»), 12, 13 основной спеки `2026-09-08-dlp-transport-core-design.md`; сборщик файлов `2026-10-05-collectors-files-usb-design.md`; конвейер событий `2026-10-05-event-pipeline-design.md`.

**Критерий завершения:** файл, скопированный на флешку на Windows-агенте, попадает на сервер ровно один раз и лежит зашифрованным; событие `file/copy` в `GET /api/v1/events` показывает `artifact_uploaded = true`; обрыв связи и извлечение флешки не теряют содержимое; повторное копирование того же файла другим агентом не передаёт байты; на хосте агент не читает файл целиком в память и укладывается в бюджет нагрузки раздела 5; `.\test.cmd` зелёный.

## 2. Принятые решения

| Решение | Выбор | Обоснование |
|---|---|---|
| Что грузится | Только `create`, `modify`, `copy` на томах типа `removable`, размером не более `max_bytes` | Содержимое на флешке исчезает вместе с ней; файлы наблюдаемых папок остаются на диске хоста |
| Кто инициирует | Агент сам | Просьба сервера приходит с задержкой heartbeat; к тому времени флешку могут вытащить |
| Офлайн | Шифрованная копия на агенте, затем загрузка с повторами | Иначе содержимое теряется именно там, где вероятнее всего утечка |
| Протокол | Докачиваемые сессии (`POST` открывает, `PUT` с `X-Offset` передаёт чанки) | Дедупликация до передачи; обрыв не начинает всё заново |
| Адресация | По SHA-256 | Один документ, скопированный многими, — один артефакт на диске |
| Шифрование на сервере | Ключ на артефакт, AES-256-GCM, ключ завёрнут мастер-ключом из окружения | Основная спека, раздел 13 |
| Признак «загружено» | Вычисляется на сервере соединением `events.artifact_sha256` с `artifacts` | Агенту не нужно перепосылать событие |

## 3. Агент

### 3.1 Отбор файлов

Решение принимается в конвейере `filewatch` после хеширования. Файл ставится в очередь загрузки, если выполнены все условия:

1. том события — `removable`;
2. действие — `create`, `modify` или `copy` (не `delete`, не `rename`);
3. хеширование завершилось успешно (`HashOK`);
4. размер не больше `collectors.artifact.max_bytes` (по умолчанию 50 МиБ);
5. `collectors.artifact.enabled` не выключен;
6. не исчерпан бюджет копирования (раздел 5).

Размер известен из `stat` до чтения, поэтому крупный файл не копируется вовсе, событие уходит как раньше.

### 3.2 Копия-подготовка

Содержимое записывается в `<data-dir>/staging/<sha256>.enc` в том же проходе, что и хеширование: читаемые байты одновременно попадают в хеш и в шифрующий писатель. Второго чтения флешки нет. Шифрование потоковое, AES-256-GCM по блокам с отдельным nonce на блок и номером блока в связанных данных, ключ — `buffer.key` (тот же, что у буфера событий, права выставляет `platform.Guard`). Имя файла — хеш, поэтому один и тот же файл не копируется дважды. Хеш события считается по тем же байтам, что попали в копию, поэтому файл, менявшийся во время чтения, даёт согласованную пару «хеш и копия» для того, что было прочитано. Целостность при передаче проверяет сервер (4.3).

Каталог ограничен `staging_max_bytes` (по умолчанию 500 МиБ). При нехватке места вытесняются самые старые копии, потеря фиксируется событием `agent/artifact_dropped` (по образцу `agent/events_dropped`). Каталог наблюдателем файлов не отслеживается (как и весь рабочий каталог агента).

Предел каталога действует по принципу «лучшее из возможного»: `staging_max_bytes` обеспечивается вытеснением самых старых копий в начале каждой новой копии; копии, которые не удалось удалить (например, удерживаемые открытыми в Windows), пропускаются. Store рассчитан на то, что копии начинаются из одного цикла наблюдателя файлов.

### 3.3 Очередь и отправка

Пакет `internal/artifacts` содержит очередь копий (она восстанавливается сканированием `staging/` при старте) и воркер. Воркер один, обрабатывает один файл за раз. Ответ сервера, не продвигающий смещение (`202` с `received_bytes` не больше текущего смещения), и повторный `409` считаются ошибкой с нарастающей паузой: воркер никогда не зацикливается на одном файле. Состояние повторов очищается для копий, которые исчезли. Потери агент сообщает событием `agent/artifact_dropped` (один раз на пачку потерь). Его запускает `runner` рядом с отправкой событий, но не в её цикле: загрузка не должна задерживать heartbeat и команды.

Для файла воркер выполняет:

1. `POST /gateway/v1/artifacts` с `{sha256, size}`.
   - `200 {"status":"exists"}` — байты не нужны, копия удаляется;
   - `201 {"upload_id", "received_bytes", "chunk_size"}` — начинается или продолжается передача.
2. `PUT /gateway/v1/artifacts/{upload_id}` чанками по `chunk_size` (до 1 МиБ), `X-Offset` равен числу уже принятых байт. Чанк расшифровывается из копии и отправляется потоком; в памяти не больше одного чанка.
3. Ответ `201` на последний чанк — артефакт принят; копия удаляется.

### 3.4 Ошибки агента

| Ответ или состояние | Поведение |
|---|---|
| нет связи, `5xx`, `429` | копия сохраняется; повтор с нарастающей паузой (как у событий) |
| `503` из-за отсутствия мастер-ключа на сервере | как временная ошибка |
| `401`, `403`, `408` | временная ошибка: копия сохраняется, повтор с нарастающей паузой, потерей не считается. Отказ на уровне всего шлюза (ротация сертификата, сбой прокси или mTLS, отозванный агент) не должен необратимо удалять все копии |
| `413`, прочие `4xx` кроме перечисленных | копия удаляется, запись в журнал агента |
| `409` | агент берёт `received_bytes` из тела ответа и продолжает с него |
| `422` (хеш не сошёлся) | сессия сбрасывается, один повтор с начала; при повторной неудаче копия удаляется |
| `404` на `PUT` (сессия истекла) | заново `POST` |

## 4. Сервер

### 4.1 Схема БД

Миграция Alembic:

```
artifacts
  id uuid PK · sha256 text UNIQUE · size bigint · storage_path text
  key_wrapped bytea · wrap_version smallint
  first_seen_at timestamptz · first_agent_id uuid FK agents(id)
  ref_count int · scan_status text DEFAULT 'pending'

upload_sessions
  id uuid PK · agent_id uuid FK agents(id) · artifact_sha256 text
  expected_size bigint · received_bytes bigint · temp_path text
  created_at timestamptz · expires_at timestamptz
  UNIQUE (agent_id, artifact_sha256)
```

Обёртка ключа — AES Key Wrap (RFC 3394): она детерминирована и nonce не требует, поэтому колонки `key_nonce` нет.

`scan_status` читает воркер подпроекта B2. `ref_count` увеличивается при каждом `exists`-ответе агенту (сколько раз артефакт предъявляли). `ref_count` считает, сколько раз сервер ответил `exists` или завершил загрузку для хеша (предъявления), а не число различных ссылок; подпроект хранения и инспекции не должен использовать его для решения об удалении. Событие хранит только `artifact_sha256`; колонка `artifact_id` и связь с вердиктами добавляются миграциями B2.

### 4.2 `POST /gateway/v1/artifacts`

Аутентификация — `current_agent`. Тело `{sha256, size}`:

- `sha256` — 64 строчных шестнадцатеричных символа, `size` — целое от 0 до `artifact_max_bytes` (серверный предел, по умолчанию 50 МиБ, при превышении `413`);
- артефакт с таким `sha256` существует — `200 {"status":"exists"}`, `ref_count` увеличивается;
- у этого агента уже есть открытая сессия на этот хеш — она возвращается с текущим `received_bytes` (`201`, докачка);
- иначе создаётся сессия со сроком жизни `upload_session_ttl_hours` (по умолчанию 24 ч) и временным файлом.

Сессия принадлежит агенту: другой агент не может писать в чужую, даже зная `upload_id` (`404`).

### 4.3 `PUT /gateway/v1/artifacts/{upload_id}`

Заголовок `X-Offset`, тело — байты чанка (не больше `chunk_size`, иначе `413`):

- `X-Offset` не равен `received_bytes` — `409` с телом `{"received_bytes": N}`;
- чанк дописывается во временный файл; `received_bytes` обновляется;
- когда `received_bytes == expected_size`, сервер считает SHA-256 временного файла:
  - совпал — файл шифруется и перемещается в хранилище, создаётся запись `artifacts`, сессия удаляется, ответ `201`;
  - не совпал — сессия и временный файл удаляются, ответ `422`;
- промежуточный чанк отвечает `202 {"received_bytes": N}`.

Параллельные `PUT` одной сессии сериализуются блокировкой строки сессии.

### 4.4 `ArtifactStore`

Интерфейс (шов, как `Queue` и `SearchIndex` основной спеки). Методы синхронные: шифрование и файловый ввод-вывод блокирующие, вызывающий код оборачивает их в `asyncio.to_thread`.

```python
class ArtifactStore(Protocol):
    def put(self, sha256: str, source: Path) -> StoredArtifact: ...
    def open(self, sha256: str, key_wrapped: bytes) -> Iterator[bytes]: ...
    def exists(self, sha256: str) -> bool: ...
    def delete(self, sha256: str) -> None: ...
```

Реализация `FileArtifactStore`: путь `BG_ARTIFACT_PATH/ab/cd/<sha256>.enc` (шардирование по первым четырём символам хеша). Шифрование потоковое, AES-256-GCM по блокам, для каждого артефакта свой случайный 256-битный ключ; ключ оборачивается мастер-ключом (AES-256 key wrap) и хранится в `artifacts.key_wrapped`. Мастер-ключ читается из `BG_ARTIFACT_MASTER_KEY` (32 байта в base64) или из файла `BG_ARTIFACT_MASTER_KEY_FILE`, но не из БД. Если ключ не задан, эндпоинты загрузки отвечают `503 {"detail": "artifact storage not configured"}`, остальной шлюз работает. `wrap_version` оставляет место для смены мастер-ключа.

Запись атомарна: временный файл в том же каталоге, `fsync`, затем `rename`. Права на каталог — только пользователь сервера.

### 4.5 Чтение и очистка

- `GET /api/v1/events`: в каждое событие добавляется булево поле `artifact_uploaded` — результат `EXISTS` по `artifacts.sha256`. Контракт и сгенерированные типы консоли обновляются.
- Просроченные `upload_sessions` и их временные файлы удаляются при старте приложения и раз в час.
- Скачивания содержимого через API нет (см. 1.2).

### 4.6 Конфигурация

Раздел `collectors.artifact` документа конфигурации агента (умолчания на сервере и в агенте совпадают, как у `file_watch`):

| Ключ | Умолчание | Назначение |
|---|---|---|
| `enabled` | `true` | Выключатель загрузки |
| `max_bytes` | 52 428 800 | Предельный размер файла |
| `staging_max_bytes` | 524 288 000 | Предел каталога копий на агенте |
| `upload_bytes_per_second` | 2 097 152 | Ограничение скорости отправки |
| `stage_bytes_per_minute` | 209 715 200 | Бюджет копирования в минуту |

Серверные настройки (окружение): `BG_ARTIFACT_MASTER_KEY` (или `_FILE`), `BG_ARTIFACT_PATH`, `BG_ARTIFACT_MAX_BYTES`, `BG_UPLOAD_SESSION_TTL_HOURS`.

## 5. Бюджет нагрузки на хост

Требование: агент не должен ощутимо нагружать рабочую станцию.

| Мера | Содержание |
|---|---|
| Один проход чтения | Копия пишется вместе с хешированием; флешка второй раз не читается |
| Память | Буфер 1 МиБ на чанк; файл целиком не загружается ни при копировании, ни при отправке |
| Один воркер | Один файл за раз; воркер не работает в цикле сборщика и не блокирует heartbeat |
| Приоритет | Поток воркера на Windows переводится в фоновый режим (`SetThreadPriority` + `THREAD_MODE_BACKGROUND_BEGIN`: ниже приоритет процессора, ввода-вывода и памяти); на других платформах не требуется |
| Скорость | `upload_bytes_per_second` ограничивает отправку |
| Бюджет копирования | `stage_bytes_per_minute`: сверх него файл пропускается, событие получает `labels.artifact_skipped = "rate"`, итог фиксируется `agent/artifact_dropped`. Так копирование сотен гигабайт на флешку не нагружает агент |
| Уступчивость | На `429` и `503` пауза с нарастанием |
| Потолок диска | `staging_max_bytes` и вытеснение старых копий |

## 6. Проверка

- **Агент (Go):** тесты отбора файлов (тип тома, действие, размер, лимиты); потоковая копия с проверкой хеша; очередь и её восстановление из `staging/`; докачка и все ветки раздела 3.4 на `httptest` с настоящим TLS; тест на память — читатель, падающий при попытке прочитать больше одного чанка за раз; тест лимитов скорости и бюджета копирования на подставных часах.
- **Сервер (pytest):** создание и докачка сессии; несовпадение смещения; несовпадение хеша; дедупликация (`exists`); изоляция сессий между агентами; предел размера; отсутствие мастер-ключа (`503`); на диске нет открытого текста (содержимое файла в хранилище не находится поиском по байтам); расшифровка возвращает исходные байты; очистка просроченных сессий; `artifact_uploaded` в `GET /events`.
- **Контракт:** `api/gateway-v1.yaml`, `test_openapi_contract`, `npm run types`.
- **Сквозная:** контур агент → nginx → сервер проверяется вручную (раздел «Ручная проверка» в `docs/COLLECTORS_MANUAL.md`): агенты стенда работают на Linux и копий не снимают, а загрузка идёт по mTLS, которого нет у локального uvicorn. Автоматически его покрывают серверные тесты (`test_artifact_upload.py`) и тесты транспорта агента на `httptest` с настоящим TLS.
- **Вручную:** Windows-агент, копирование файла на флешку, обрыв связи до и во время загрузки, извлечение флешки; описание в `docs/COLLECTORS_MANUAL.md`.

## 7. Риски

| Риск | Смягчение |
|---|---|
| Копии на диске хоста содержат конфиденциальное | Шифрование ключом агента, права `platform.Guard`, удаление после загрузки, потолок каталога. Остаётся открытым вопросом защита самого `buffer.key` через DPAPI |
| Файл изменился во время чтения | Хеш и копия получены одним проходом и согласованы; при передаче целостность проверяет сервер (`422`) |
| Хранилище артефактов — самая ценная цель на сервере | Шифрование на артефакт, мастер-ключ вне БД и вне каталога данных; права на каталог |
| Рост хранилища без срока хранения | До B2 хранилище только растёт; предел размера файла и дедупликация сдерживают рост; срок хранения вводится в B2 |
| Злоупотребление загрузкой (много сессий) | Ограничение частоты в nginx, предел размера, срок жизни сессий, уникальность `(agent_id, sha256)` |
