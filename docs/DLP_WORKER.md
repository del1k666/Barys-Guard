# Воркер инспекции содержимого (DLP)

Воркер берёт файлы, загруженные агентами с внешних томов, достаёт из них текст, проверяет правилами и создаёт вердикты и инциденты.

## Как это работает

1. Агент копирует файл на флешку и присылает событие `file/copy`; содержимое загружается отдельно и хранится зашифрованным.
2. Когда есть и событие, и содержимое, событие ставится в очередь (`event_queue`).
3. Процесс `barysguard-admin worker` забирает задачи, расшифровывает файл в памяти, извлекает текст и ищет:
   - **ИИН/БИН** (12 цифр, проверяются дата и контрольный разряд);
   - **банковские карты** (13–19 цифр, проверка Луна и префикс сети: Visa, Mastercard, МИР, Amex);
   - **грифы** из словаря «Грифы» («конфиденциально», «для служебного пользования», «коммерческая тайна» и др.).
4. По находкам считается оценка: вклад правила = вес × min(число совпадений, потолок), итог не больше 100.

| Оценка | Вердикт | Критичность |
|---|---|---|
| 0–19 | `clean` | `info` |
| 20–49 | `flagged` | `medium` |
| 50–79 | `flagged` | `high` |
| 80–100 | `flagged` | `critical` |

Формат определяется по содержимому файла (подписи PDF, OLE и zip, состав архива Office), а не по имени: документ Word, переименованный в `.txt`, проверяется как документ. Расширение — лишь подсказка для текстовых файлов (`.txt`, `.csv`, `.json` и т. п.).

Файл, который не удалось проверить (неподдерживаемый формат, архив, документ без текста, защищённый паролем, повреждённый, с распакованным или извлечённым содержимым сверх пределов `BG_INSPECT_*` — причина `too_large`), получает вердикт `not_inspected` с причиной. Он не теряется, но и инцидента не создаёт.

Файлы крупнее `BG_ARTIFACT_MAX_BYTES` (по умолчанию 50 МиБ) на сервер не загружаются вовсе (сервер их не принимает), поэтому вердикта у таких событий нет: в карточке события содержимое помечено «Не загружено».

Инцидент создаётся, когда оценка не ниже `BG_INCIDENT_MIN_SCORE` (по умолчанию 20). Копии одного файла с одной машины одним пользователем собираются в один инцидент, пока он не закрыт.

Правила (вес, потолок, включение, свои словари и шаблоны) настраиваются в консоли: «Правила», только администратор. Подробная инструкция — [RULES_GUIDE.md](RULES_GUIDE.md).

В базе хранятся счётчики, маски (ИИН/БИН — две последние цифры, карта — четыре последние) и короткие маскированные фрагменты текста вокруг находок; полные значения не сохраняются никогда.

### Фрагменты

- На каждое правило вердикт хранит до 5 фрагментов (`before`, `hit`, `after`) из первых совпадений по порядку в тексте; контекст — около 80 символов с каждой стороны (считаются исходные символы, поэтому в тексте с большим числом пробелов, например в таблицах PDF, контекст может быть короче).
- `hit`: для ИИН/БИН, карт и правил-шаблонов — маска; словарные термины показываются как в тексте (с исходным регистром).
- Чувствительные значения в окружающем тексте заменяются такими же масками. Дополнительно, как независимая страховка, «чистильщик цифр» убирает из контекста любую последовательность из 5 и более цифр (в том числе с пробелами, дефисами и похожими разделителями) и любую цифровую последовательность, примыкающую к `hit` или к обрезанному краю, заменяя её на «•». Поэтому обычные длинные числа, даты и телефоны в контексте тоже затираются; короткие группы до 4 цифр могут остаться (например, префикс эмитента перед маской карты).
- Края, разрезавшие слово или число, отбрасываются и отмечаются «…».
- Сканер хранит дополнительную историю (`80 + max(40, длина самого длинного маскируемого значения)` символов, 280 при наличии правила-шаблона), поэтому фрагмент не зависит от того, как текст разбит на порции.

## Запуск

```bash
barysguard-admin seed-rules   # завести встроенные правила (идемпотентно)
barysguard-admin worker       # запустить воркер (нужны BG_DATABASE_URL, BG_ARTIFACT_PATH, BG_ARTIFACT_MASTER_KEY)
```

На стенде воркер — сервис `worker` в `docker-compose`, правила заводятся при старте. Чтобы увидеть инциденты на стенде, выполните `.\stand.cmd seed`: агентам добавятся события копирования двух демо-файлов (с ИИН и картой, и безобидный). Через несколько секунд:

```
GET /api/v1/incidents
```

## Развёртывание

- Для правил-шаблонов нужна библиотека `google-re2` (указана в зависимостях сервера, `server/pyproject.toml`); ей нужны бинарные колёса или установленная RE2.
- Выполните `barysguard-admin seed-rules` один раз до запуска воркера. Пока правил нет, воркер не берёт задачи из очереди и пишет в журнал ошибку: иначе все файлы получили бы вердикт «чисто».
- Миграция строит индекс `ix_events_artifact_sha256` по секционированной таблице `events` без `CONCURRENTLY`, то есть с блокировкой записи на время построения. На большой боевой таблице применяйте её в окно обслуживания.
- Таймаут извлечения (`BG_INSPECT_TIMEOUT_SECONDS`) кооперативный: он проверяется между порциями текста и страницами и не прерывает разбор одного XML-элемента или одной страницы PDF. Задайте контейнеру воркера предел памяти.

## Настройки

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `BG_WORKER_BATCH` | 10 | задач за один захват |
| `BG_WORKER_POLL_SECONDS` | 2 | пауза при пустой очереди |
| `BG_WORKER_LOCK_SECONDS` | 300 | сколько воркер владеет задачей |
| `BG_WORKER_MAX_ATTEMPTS` | 3 | попыток до вердикта «ошибка» |
| `BG_INSPECT_MAX_TEXT_BYTES` | 20971520 | предел извлечённого текста |
| `BG_INSPECT_MAX_UNPACKED_BYTES` | 209715200 | предел распаковки контейнера Office |
| `BG_INSPECT_MAX_ENTRIES` | 10000 | предел элементов контейнера |
| `BG_INSPECT_MAX_RATIO` | 100 | предел степени сжатия (для элементов крупнее 1 МиБ) |
| `BG_INSPECT_TIMEOUT_SECONDS` | 30 | таймаут на файл |
| `BG_INCIDENT_MIN_SCORE` | 20 | порог создания инцидента |

## Словарь грифов

Словарь грифов — обычное словарное правило: термины добавляются и удаляются в консоли («Правила» → «Грифы»), подробности в [RULES_GUIDE.md](RULES_GUIDE.md). Регистр и `ё/е` не важны. Встроенные термины кладутся только при первом запуске `seed-rules`, когда словарь создаётся; дальше словарь принадлежит оператору, а повторный запуск `seed-rules` не перезаписывает правки оператора (термины, вес, потолок, включение) и не возвращает удалённые термины. Каждая правка создаёт новую версию правила, новые файлы проверяются по обновлённому набору, старые события заново не оцениваются.

Сокращение «ДСП» во встроенный словарь не входит: оно же означает древесно-стружечную плиту и давало ложные срабатывания. В установках, где словарь заведён раньше, термин `дсп` остаётся, пока его не удалят из словаря (после удаления — `seed-rules`).

## API

- `GET /api/v1/incidents` — фильтры `status`, `severity`, `agent_id`, курсор.
- `GET /api/v1/incidents/{id}` — вердикт, совпадения (счётчики и маскированные образцы; каждое совпадение содержит `weight`, `cap` и `fragments` с полями `before`, `hit`, `after`), события. Список инцидентов фрагменты не возвращает.
- `PATCH /api/v1/incidents/{id}` — `{"status": "acknowledged" | "closed"}`, действие пишется в журнал аудита.
- `GET /api/v1/events` — у событий с содержимым есть поле `verdict`.

## Консоль

Инциденты видны в разделе консоли «Инциденты»: список с фильтрами, карточка с совпадениями (маскированные образцы) и событиями, кнопки «Принять» и «Закрыть». В списке «События» у событий с содержимым есть колонка «Вердикт».

## Ограничения этой версии

Нет архивов, OCR, YARA, редактора правил; вердикты старых событий при смене правил не пересчитываются; формат `.doc/.xls/.ppt` (OLE) не поддерживается.

Вердикты, созданные до появления фрагментов, их не содержат (пустой список, `weight` и `cap` равны 0) и не пересчитываются.

Ограничения фрагментов:

- слишком длинное совпадение пользовательского правила-шаблона (длиннее допустимой длины совпадения) не засчитывается как находка, а его текст может попасть в контекст другого фрагмента без маски;
- секреты, состоящие только из букв, защищены лишь маскированием по правилам;
- разделители между цифрами, кроме пробелов, дефисов и нескольких знаков препинания, детектор карт тоже не распознаёт.
